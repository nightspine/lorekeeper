# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Lorekeeper is a draft open standard (SPEC.md) for spoiler-gated book indexes ("X-Ray"-style companions), plus a Python reference implementation. The spec is the product; the Python code exists to make the spec testable and to serve later as the basis for a self-hosted server and generator. Reader apps (KOReader, iOS readers) are meant to consume indexes without any AI.

## Commands

```sh
uv sync                                   # install (Python ≥3.11, deps: jsonschema; dev: pytest)
uv run pytest                             # all tests
uv run pytest tests/test_gating.py::test_cross_book_replacement   # one test
uv run lorekeeper conformance             # run conformance cases
uv run lorekeeper conformance --update    # regenerate expected views after an intended gating change
uv run lorekeeper validate examples/sherlock-holmes/study-in-scarlet.json examples/sherlock-holmes/sign-of-four.json --series examples/sherlock-holmes/series.json
uv run lorekeeper validate examples/sherlock-holmes/study-in-scarlet.json --epub corpus/pg244/pg244.epub   # + anchor & quote checks
uv run lorekeeper blocks corpus/pg244/pg244.epub --start 100 --end 150    # list blocks (seq, spine, words, fp, text) for authoring
uv run lorekeeper fill-anchors INDEX --epub EPUB --write                  # compute fp from seq hints, record edition hashes
uv run lorekeeper toc corpus/pg244/pg244.epub                             # chapter numbers for --chapters
uv run lorekeeper generate corpus/pg244/pg244.epub -o out.lore.json --chapters 5-6   # needs Ollama running
uv run lorekeeper generate ... --resume                                   # continue an interrupted run
uv run lorekeeper generate ... --provider gemini --model gemini-2.5-flash # bring your own key: claude|openai|gemini|openrouter|mistral|groq|xai|deepseek|custom (key from the env var, or --api-key-file PATH; --base-url for custom)
uv run lorekeeper profiles INDEX... --tidy                                # older indexes: drop description-entities, backfill profiles (Claude; backups first)
uv run --extra claude lorekeeper portraits INDEX...                        # rewrite profiles from every passage mentioning each entity (Haiku; --prior earlier books; backups first)
uv run python bench/model_bakeoff.py MODEL...                             # compare Ollama models on one passage
uv run --extra web --extra claude lorekeeper web                          # Library, Reader, Runs UI on :8765
uv run lorekeeper web --no-auth                                        # skip the web app sign-in (trusted local use only; or env LOREKEEPER_AUTH=off)
uv run lorekeeper reset-password [--data DIR]                             # new generated admin password, printed once; forces a change and ends all sessions
uv run lorekeeper web --api-token TOKEN                                # require a bearer token on /v0 (or --api-token-file PATH, or env LOREKEEPER_API_TOKEN)
uv run lorekeeper docs export build/                                      # landing page (site/) + docs + spec + styles, for hosting
docker compose up -d                                       # same server in a container on :8765, data in the lorekeeper-data volume (env: LOREKEEPER_DATA/HOST/PORT/OLLAMA_URL/API_TOKEN)
node tests/js/run_conformance.mjs                                         # JS gating vs conformance cases
uv run python bench/compare_handwritten.py out.lore.json                  # generated vs hand-written example
```

The generator needs a local Ollama (`brew services start ollama`), or a cloud provider with your own key (every provider in `llm.PROVIDERS`: `llm.OpenAICompatible` serves all but Claude, which uses the anthropic SDK). Default model is `gemma4:12b-it-qat`; `qwen3.5:9b-q4_K_M` is the faster alternative. Thinking mode is deliberately off. A two-chapter run takes tens of minutes on a 16 GB M4, so run it in the background. Tests use a scripted fake model (`tests/test_generate.py`) and never call Ollama.

`corpus/` is gitignored; the README lists the download commands (pg244, pg2097, pg345 and the Standard Ebooks Scarlet). `examples/dracula/dracula.json` is a complete generated index of pg345 that the Library, the Docker image and the landing-page demo ship with; it must pass `lorekeeper validate --epub corpus/pg345/pg345.epub`, and `bench/site_demo_data.py` flattens it for the site. Tests that need a corpus EPUB skip when it is missing, so a green run without the corpus doesn't cover anchor resolution or quote checks.

## Architecture

The pipeline, in spec order:

1. **Text model** (`epub.py`, SPEC §3.1): EPUB spine → paragraph-level blocks → `seq` numbers. Standard library only (zipfile, ElementTree, html.parser). A document with no `p`-style blocks but real text (Calibre's `<div class="p">` paragraphs) is re-parsed with `div`/`blockquote`/`section`/`article`/`aside` as blocks (`FALLBACK_BLOCK_TAGS`, §3.1 rule 6); it only ever applies per document, so books that already parse keep their seqs and text hashes.
2. **Normalization and fingerprints** (`text.py`, §3.2–3.4): `words()` and `fingerprint()` are the cross-language contract. Every port (Lua, Swift, Kotlin) must produce identical output. Any change here changes every anchor in every index: run `fill-anchors` on the examples and update SPEC §3.2.
3. **Anchor resolution** (`anchors.py`, §3.6–3.7): the client side. It maps a reader's own edition onto an index's ordered anchors. Unresolved anchors take the *next* resolved anchor's location, so mismatched editions can only under-reveal. Keep that invariant.
3b. **Locators** (`locators.py`, §3.7): `locate(book, locator)` turns what a reader app holds (`{"block"}`, `{"cfi"}`, `{"xpointer"}`, `{"spine","word"}`, `{"spine","progress"}`) into the seq of the block it points into, rounding to the *preceding* block when in doubt (-1 before the first block; `exact=False` when a fallback decided), and `position(..., inclusive=)` gives the current anchor in the two modes: "finished" (the current block does not count, for views) and inclusive ("who is this on my page?"). `web/position.py` (Book Orbit) is built on it. Cross-language vectors live in `conformance/locators/` (run by `lorekeeper conformance`; skipped when the corpus EPUB is missing).
4. **Gating** (`gating.py`, §7): `view(indexes, Position, series, order, finished)` is the normative algorithm. Its output shape is `schema/view.schema.json` and is what `conformance/*.json` freezes.
5. **Generation** (`generate.py`, `llm.py`): `llm.PROVIDERS` is the one table of cloud providers (label, kind `anthropic`/`openai`, base URL, key env var, key URL, preset models with prices and a `cheap`/`strong` tier); it is the only place to update model ids and prices, and a stale preset never blocks anything because the UI also lists live models from `GET {base_url}/models`. `llm.make(provider, model, api_key, base_url)` dispatches on it. `OpenAICompatible` is stdlib-only: json_schema first, plain json_object with the schema in the prompt after a 400, and it adapts to models that reject `max_tokens` or `temperature` on the first 400; unpriced models cost 0 in `Usage` and show "price unknown" in the UI, never a made-up number. It reads chapters (from the EPUB table of contents, `epub.read`) in chunks of whole blocks. Per chunk: one extraction call, a rephrase call if a claim copies 9+ words of the book, one support-check call. Facets describe what an entity *is* (role, look, nature, allegiances, status); plot goes to events. The extraction also returns **profiles**, for every new person, creature and group and for anything it learns something lasting about (a new entity's one-sentence `desc` reads like the first line of a character sheet and, when the response has no profile for that entity, is committed as its first profile instead of a plain fact; with a profile it is dropped as a duplicate): a self-contained "who this is now" for entities whose picture changed, committed as `kind: "profile"` facets that replace the entity's current profile, including one inherited from an earlier series book, so a character keeps one growing description (the Reader shows the latest visible one). Those extraction profiles are pieced together one passage at a time; `portraits.py` rewrites them afterwards the way a reader would: at each chapter end, for every entity mentioned at least 2 times (rewritten once at 4 mentions if the first came from fewer, then again once mentions grow by half, and at the next chapter end after a checked fact records a change in standing, `portraits.STATUS`: died, married, captured, revealed...; a thin tie or role is stated plainly), it sends the paragraphs around every mention so far (up to 40, sampled evenly, first and last kept; a name counts only if no other entity shares it, so "Harry" but not "Potter") together with the entity's last 8 checked facts, and asks for a character-sheet description, not a plot summary, whose first sentence states any lasting change in standing the passages show ("Dead, killed by..."); a change in standing recorded since the last portrait, as a checked fact or as a turning point naming the entity ("Lucy dies"; `changes_standing`, which ignores hedged phrases such as "near death" or "fears she is dead", `HEDGED`), is quoted in the prompt, the portrait is never revealed before it, and one whose first sentence does not state it (a death needs a death word, `DEATH`; "engaged" does not count) gets one rewrite ("rewritten: change in standing"); a rewrite may not drop a death the previous portrait opened with: one retry, else the previous portrait stands ("dropped: lost the change in standing"). Only text up to that point is sent and the portrait is revealed at the first anchor after the last paragraph used. A portrait naming a word the book hasn't used yet (model memory) is dropped; "now"-style wording gets one rewrite. A profile, desc or portrait that states a tie (wife, fiancée, mother, heir: `generate.TIE_WORDS`) the passage or the entity's notes never use is dropped ("dropped: tie not in the text"; portraits get one rewrite first, and for them the sampled passages, the entity's checked notes and profiles up to that point and the previous portrait all count as support), because models upgrade "someone Harker keeps notes for" to "Harker's fiancée" from memory. Portraits replace extraction profiles from their first one's reveal point on (one at that same anchor goes too); earlier ones stay as the early description, and a rewrite that lands on the previous portrait's anchor stands in for it rather than sitting beside it. Every finished web run writes them as a last "Writing descriptions" stage (`JobManager._portraits`: the cheap model of the run's own cloud provider, else of the first configured one, about 20 cents a novel on Haiku, skipped without any cloud key; a failure there keeps the index as the run wrote it). Names must appear in the passage (a name the model knows from elsewhere is dropped: it could name someone before the text does); a new entity is introduced at the first verbatim use of its name in the indexed text (`earliest_mention`), never later than needed; people named together ("Mr. and Mrs. X") are split into two (`split_couple`); matching (`match_known`) respects titles (Mr/Mrs never match), plural and reordered forms, a full name for someone known only by title and surname, a tail form ("Van Helsing" / "Abraham Van Helsing") and middle names or initials (`merge.same_person_name`). A proposed name goes through `resolve_name`: when it fits two or more known people (`ambiguous`), it never creates a third entity; if the hits all match each other by name and nothing forbids it (`_may_merge`: no `Options.distinct` pair, no relation between them, no title of another sex, no two different full proper names) they are folded into one in-run (`_merge_entities`, logged in `added` as kind "merge", stat "merged by a bridging name"); otherwise a small `DISAMBIGUATE` call over the three paragraphs around the name picks one, "both" or "none" (at most `MAX_DISAMBIGUATE` per chunk), as it does for a new bare first name while a person known only by title and surname is in the passage. The model's `names` list is not trusted: each entry is a (name) claim in the fact-check, a name already carried by another entity is never added to a second one, and a bare family surname is never a name, and a person never takes a name the text gives a relative (`names_a_relative`: "her mother Mrs. Westenra", "daughter of Mrs. Westenra" in the cited paragraphs or the entity's notes) or, for a titled name, one any sentence read so far uses beside the entity's own name as a second person (`names_two_people`: "Mrs. Westenra was anxious concerning Lucy"), stat "dropped: name of a relative". `earliest_mention` searches a titled name only in its exact form ("Mrs. Harker" must not inherit chapter one from "Jonathan Harker"). The fact-check (`VERIFY`, optionally a stronger `Options.check_llm`) gives every claim a verdict with a one-line reason: `unsupported` drops it (kept with its reason under `rejected` in the `.report`), `unsure` keeps it but lists it under `unsure` (stat "kept: checker unsure"), and a claim with no verdict is accepted; it sees earlier chapter recaps for recap claims and moves facts that narrate a moment into events, except descriptions (`DESCRIPTIVE`, "A tall man in black who..."), which stay facts. Events are every development that changes the situation, up to `max(6, words/200)` per chunk, each weighed by the model as `turn` (a turning point: revelation, twist, reversal, realization, death, a decision with no way back), `plot` (an ordinary development, stored as no `kind`) or `minor` (a small moment; `EVENT_KINDS`, SPEC §4.4), and the prompt names the chapter the passage is from. The chapter summary asks for complete sentences on what the passage does to the story, leaving out scenery, meals and travel details; a summary sentence or event under `MIN_SENTENCE_WORDS` words (a heading or a label such as "unresolved") is dropped ("dropped: not a sentence"); a chunk whose summary comes back empty gets a chapter recap made of its own checked events, minor ones left out ("chapter recap from events"). The context block lists each mentioned entity's existing ties (`_ties`), and the prompt asks for a relation only when the companion lacks it or the passage changes it. A relation is a lasting tie, never one action, with a `kind` (`RELATION_KINDS`: family, romance, friendship, alliance, service, hostility, acquaintance, place; SPEC §4.3): a label over `MAX_TIE_WORDS` is dropped ("dropped: not a tie"), a passage keeps one tie per pair and kind, the one shown latest ("dropped: second tie for a pair"), the fact-check lists ties that narrate one action under `moments` and they are dropped ("dropped: an action, not a tie"), and a new tie of the same kind between the same two `replaces` the current one (`_current_tie`, "ties replaced by a newer one"), so "fiancée of" becomes history when "wife of" arrives. The story recap walks the whole arc so far and then the recent stretch (up to 10 sentences); a recap or summary that talks about "this passage" is dropped (`ABOUT_THE_TEXT`) and the previous one stays. Chunk size defaults to `default_chunk_words(provider)`: 8,000 words (about a chapter) for a cloud provider, 2,500 for Ollama; the build form and the CLI follow the provider unless a size was chosen. The Claude backend sends no sampling parameters (the API rejects `temperature` since 2026-10-21); Ollama and OpenAI-compatible backends use 0. Proposed names pass `triage_name` first: possessive descriptions of things ("Gabriel's fear") are dropped, descriptions wrapped around a name ("Celene's brother Gabriel", "Chevalier of the Golden Host (Gabriel)") resolve to that entity; unnamed people ("Gabriel's daughter") stay. The extraction also returns a story-so-far recap and a list of summary sentences; each sentence is fact-checked on its own and the survivors become a `scope: "chapter"` recap (one per chunk, titled with the chapter, so a long chapter has several parts the Reader joins). The model only proposes content. Python assigns anchors, ids and reveal points: `from` = the last cited block, then snapped *forward* to the next anchor-eligible block (≥ 6 words, unique fingerprint). Python also matches names (`match_known`, `mentioned`: exact, without honorifics, or a unique surname) and drops anything that fails a check. The index and a `.state` sidecar are written after every chunk, which is how `--resume` works. A `.report` sidecar holds drop counts by reason.

They are only ever returned masked and are passed to backends at run time, never stored in job config or events. `GET /api/providers` lists every provider (configured, source, masked key, preset and live models), `PUT /api/providers/{id}` tests the key with a free call (`GET /models`, or `models.list` for Claude) and refuses one that fails, `DELETE` removes it, and `/api/providers/anthropic` and `/api/claude` stay as aliases of `claude`. Job config `provider` is any registry id (or `ollama`). The duplicate checker uses the first configured cloud provider's cheap model (its strong model for the second opinion), Claude first, else Ollama. A run fills `Options.distinct` from the catalog's "not the same" pairs (`distinct_for`).
   **Sign-in** (`web/auth.py`, on by default; `create_app(auth=False)` or `--no-auth` / `LOREKEEPER_AUTH=off` disables it and prints a warning; tests that don't test auth pass `auth=False`): one account, `admin`, shaped so more users can come. The first start with no users creates it with `LOREKEEPER_ADMIN_PASSWORD` when set, else `secrets.token_urlsafe(12)`, prints it once, and sets `mustChangePassword` in both cases. While that flag is set every protected route except `/api/auth/*` answers 403 `{"detail", "code": "password-change-required"}`, enforced server-side. Store: `lorekeeper-data/auth.json` (0600, atomic write like `secrets.py`): `users.<name>` = `{hash, mustChangePassword, created, changed}` and `sessions.<sha256 hex of token>` = `{user, created, seen}`. Hash: stdlib `hashlib.scrypt` n=2**15, r=8, p=3, 16-byte salt, stored as `scrypt$32768$8$3$<salt>$<hash>` (base64url) so parameters can change; compared with `hmac.compare_digest`; an unknown username still runs one scrypt. Policy: 12 to 128 characters, no composition rules, must differ from the current one. Sessions: cookie `lorekeeper_session` (`token_urlsafe(32)`, only its sha256 is stored), 30 days idle (`seen` refreshed at most hourly) and 90 days absolute, HttpOnly, SameSite=Lax, Path=/, `Secure` when `request.url.scheme` or `X-Forwarded-Proto` is https; changing the password deletes every other session and rotates the current one, `reset-password` deletes all. Public paths: `/`, `/static`, `/docs`, `/css`, `/fonts`, `/vendor`, `/spec.md`, `/readme.md`, `/.well-known/*` (the Docker healthcheck), `/v0/*` (keeps its own bearer token) and `/api/auth/*`; everything else under `/api/`, plus `/api/docs` and `/openapi.json`, needs a session: 401 `{"detail": "Sign in required"}`. `GET /api/auth/session` always answers 200 (`{auth:false}`, `{auth:true,user:null,setup}` or `{auth:true,user:{name,mustChangePassword}}`); `login`, `logout` and `password` answer 404 when auth is off. CSRF is unchanged (`X-Lorekeeper: 1` plus SameSite=Lax). Login throttle, in memory per (username, client ip): after 5 failures the next attempt is refused for 2^(failures-5) seconds up to 15 minutes, 429 with `Retry-After`; a wrong current password on the change form counts too. Frontend: `api.js` `request()` sends a 401 to `#/login?next=<same-page hash>` and a 403 `password-change-required` to `#/password`; `app.js` awaits `api.session()` before polling or rendering (a 404 or failure means an older server, treated as auth off) and sets `body.dataset.auth` and `dataset.signedIn`; signed out, only the brand and theme toggle show and only `#/login` and `#/password` render. Styles in `css/auth.css` (after settings.css). Sign out lives in Settings, in the first "Account" card (which also has the change-password form), and in the palette's "Account" group. Keep `docs/self-hosting.html#sign-in`, SECURITY.md and the README in step with any change here.
7. **Library catalog** (`web/catalog.py`, `web/bookorbit.py`): the Library browses **books**, and index files are *versions* of a book. A version is matched to a book by its edition text hash, so it needs the book's EPUB on disk. Book Orbit books are a synced cache (`lorekeeper-data/bookorbit/books.json`) holding only books with an EPUB (comics and PDFs have no text to index), plus per-library counts. After signing in the user picks which Book Orbit libraries to show (`bookorbitLibraries` in `library.json`; absent means all, and a new connection clears it); `Catalog.bookorbit_books()` applies both filters. Their EPUB is downloaded on first build (`prepare`) and linked in `library.json`, which also holds each book's default version and manual series for uploads. Series come from Book Orbit, from EPUB metadata (`epub.read`: EPUB 3 `belongs-to-collection`, then Calibre's series meta), or from the user, and are grouped by slugged name. `preflight` reports earlier books with no index and numbering gaps (`notInLibrary`). Builds that go through the catalog get `series_id`/`book_key`, a written series manifest, and `prior` = earlier books' default indexes (`Generator._load_prior` / `_localize`: returning entities keep their ids, cross-book `replaces`, the story-so-far carries over). Front and back matter is decided once, server-side (`web/jobs.py` `NOT_STORY` / `is_story`). A run that covers every story section is marked complete (`Options.whole_story`). Book Orbit auth is username/password with `clientKind: "native"`. Only the rotating refresh token is stored (in secrets), never the password. The access token is in memory and refreshed on 401 or expiry. Lorekeeper never writes to Book Orbit: `BookOrbit._call` refuses every non-GET except the `/books/query` read before any request is made (tested), and the Reader never pushes a position back. In the Reader, a Book Orbit book that isn't finished treats the synced position as a spoiler line: the slider stops there while dragging, and any deliberate move past it (release, percent, chapter jump, next reveal) asks first (`moveTo`); "Show me anyway" allows it for that session and the source line says so, "Back to Book Orbit's position" clears it. `GET /api/library/{key}/position` (read-only) reads the user's Book Orbit reading progress for the book that owns that index (`BookOrbit.progress`: newer servers answer `GET /reading-progress?bookId=`, older ones only `GET /books/{id}/progress`, a flat row per file, normalized to the same shape) and returns `{synced, source, updatedAt, percentage, basis, seq, p}`, or `{synced: false, reason}` (`not-bookorbit`, `not-connected`, `no-edition`, `unreachable`, `no-progress`) so the Reader degrades quietly; `p` is the fraction of words before block `seq`, so the block being read never counts as read. `web/position.py` `resolve` picks the first usable of EPUB CFI (the id asserted on the target element, else the character position inside the XHTML), Kobo (spine file plus percent), KOReader XPointer and the whole-book percentage, using each `epub.Doc`'s `spine_child_index` because CFI and KOReader spine steps count `linear="no"` items too; an exact position more than 5 points away from the percentage is stale (another device moved on) and the percentage wins, and it never raises.
8. **Entity identity** (`merge.py`, `web/identity.py`): one set of name rules (`core`, `extends`: titles stripped, parenthetical notes and possessive descriptions ignored, a shorter prefix form counts for people only) is shared by `Generator.match_known` and duplicate detection. `candidates` groups matching entities across a series: groups where everyone matches everyone are `sure`, others are offered pair by pair. `merge` folds one id into another in every index of the series. It is spoiler-safe because names and facets keep their own `from`, except for hidden identities ("the stranger" is Gabriel), which must never be merged. The web layer only rewrites generated indexes, refuses while a run writes one, snapshots files to `lorekeeper-data/merges/<id>/` for undo, and keeps "not the same" pairs in `library.json` (`distinct`). The Reader suggests a pair only when both entries are visible at the reader's position. Beyond name rules, a model reading short descriptions of the cast proposes pairs the names can't show ("Mr. Dursley" / "Uncle Vernon", `merge.propose`, Haiku). Every pair, proposed or by name, is then judged (`merge.judge`, Sonnet 5.5 when a Claude key exists, else the same model as propose; `judge_model` / `strong_judge_model` in `web/app.py`) from the whole entry of each side (full latest profile, up to 8 details, up to 8 ties as sentences, where it is introduced), the paragraph where the later entry's name first occurs in the book with one paragraph either side (EPUB found by the index's `editions[].textHash`; judged without it when the EPUB is missing), and any paragraph where both names occur as separate mentions. The verdict (`same`, `different`, `unsure`) comes with a one-line `because` that is stored (state `because`, and the merge journal) but never shown to readers, since it may state whole-book facts. A pair left `unsure` without the text is judged once more when the EPUB is on disk. Bump `merge.JUDGE_VERSION` when the prompt changes. Policy (`identity.auto_ok`, `Identity.auto_merge`), all as one undoable step after each check: judged `same` merges automatically when the pair is a same or fuller name, a shared alias where at least one shared name is a proper name (`merge.proper_name`: "Aaron", "Van Helsing", not "the Professor", "the stranger", "Forever King"), or a model-proposed pair whose names are all proper names. Shared descriptors only (the shape of a hidden identity) always go to review. `different` pairs are stored and not listed. `unsure` pairs are listed as "Couldn't tell from the text". In a group where an entry fits several others ("Chloe" fits two Chloes) a pair is merged only if neither entry is in another live suggestion. Family surnames and bare titles are not evidence of identity (`merge.family_names`). Display names (`merge.rank_names`) prefer an entity's actual name over titles: a title word anywhere marks a title ("Forever King"), a shared family surname marks a real name ("Fabién Voss"); the generator applies the same ranking when a new name arrives. Measured on real books on 2026-10-28: the Empire of the Vampire series went from 137 listed pairs to 17 for review, and a fresh Dracula build leaves none.
8b. **Editing by hand** (`web/editor.py`, `web/static/js/editor.js`): the Reader's edit mode (the "Edit" button, `edit=1` in the URL; only for an index built here with its EPUB on disk) lets a person add, change and delete entries, names, details and descriptions, connections, events and recaps, and start an index from nothing ("Write it myself" on the build form, `POST /api/catalog/books/{key}/handmade` → `Editor.blank`: one anchor, no generator, contributor role `author`). Every change is one `POST /api/library/{key}/edits` with an `op` (`add-entity`, `set-type`, `delete-entity`, `add/edit/delete-name`, `-facet`, `-relation`, `-event`, `-recap`, `set-complete`) and one entry in the merge journal (`Identity._commit` with `kind: "edit"` and a `what` line), so `POST /api/library/{key}/undo/{id}` reverts edits and merges alike, and the toast after each change offers it (inside the drawer while it is open, since a modal dialog makes the page inert). Nobody types an anchor: an op names a paragraph `seq`, and `_Ctx.anchor` snaps forward to the first block with 6+ words and a unique fingerprint, reusing an existing anchor or minting one in the generator's id scheme; `coverage.through` moves forward to it when needed, an entity's `from` is always its earliest name's. `GET /api/editions/{hash}/blocks?seq=&before=&after=` feeds the paragraph picker (`eligible` says whether a block can carry an anchor). Entity-wide ops (`set-type`, `delete-entity`) reach every index of the series; item edits only the book that holds the item. Text goes through `check_wording`: the spec's length limits, `generate.HINDSIGHT`, `MOMENTARY` for descriptions only, `unsupported_tie` against the cited paragraph and its neighbours, and the 9-word copy rule (both only with the EPUB on disk); a refusal is a 422 with `code: "wording"` that the form shows under the field. Each edit is also recorded in `lorekeeper-data/edits/<textHash>.json` with its journal id and a target (entity id, item id, original text), undo removes it again, and `JobManager.after_run` (`Editor.reapply`) puts them back on every new build of the same edition: by id when it survived, else by the entity and the original text, skipping what no longer applies ("your edits: 5 applied again, 1 no longer apply" in the run log). An edited index is still a plain SPEC 0.1 document: the only trace in the file is `provenance.updated` and a contributor with role `editor` (`author` for a hand-made one).
9. **Validation** (`validate.py`, §6.4): schema check first (later checks assume a valid document), then mechanical rules, then rules that need the book (`check_against_book`) or the series (`check_series`). Passing `prior=None` to `check_index` means the earlier books weren't supplied, so cross-book references become warnings; `[]` means there are no earlier books.
10. **Clients** (`clients/`): programs that consume indexes without any AI. `clients/koreader/lorekeeper.koplugin/` is a thin KOReader plugin (Lua 5.1/LuaJIT): it sends the CREngine XPointer plus the EPUB's `fileHash` to a server's `/v0` routes ("Who is this?" on a selection, "Story so far") and shows only what comes back, without caching any view. Routes live only in `lorekeeper_client.lua`; `lorekeeper_format.lua` is pure Lua. `tests/test_koreader_plugin.py` pins its routes and query parameters to `web/protocol.py`, so change the two together. The JS gating module in `web/static/js/gating.js` (driven by `tests/js/run_conformance.mjs`) is the reference client for local gating. **Rule:** a client that implements a part of the spec (locators, anchor resolution, gating) must pass the conformance suites for that part (`conformance/`) before it counts as supporting it. Clients must never derive positions from percentages or page numbers (SPEC §3.7). A fat client (local gating in Lua) is future work (SPEC §11).

Key format ideas that span several files:
- Every gated item has a `from` anchor; comparisons use the anchor's **ordinal** (position in the `anchors` array), never ids or `seq`.
- `replaces` only points backwards (same book earlier, or an earlier series book), so indexes can be generated forward without editing earlier files. Replaced items become `history`, not deleted.
- Entity ids are series-scoped; each book's index lists only that book's names and facets, and `view()` merges across finished books. `carried` is a denormalized fallback used only when the origin book's index is absent.

## Conventions

- Content rules (SPEC §6) apply when editing example indexes: text-only claims with `evidence`, written as the reader understands things *at* the `from` anchor (no hindsight), at most 8 consecutive words quoted from the book. The validator checks the last rule with `--epub`.
- Example anchors use ids like `ch2.para14` (chapter, paragraph within chapter) with `seq` hints for the Gutenberg edition. Author new anchors by `seq`, then run `fill-anchors`.
- Conformance expected outputs are generated by the reference implementation. When regenerating, review the diff, and keep spoiler properties asserted independently in `tests/test_gating.py`.
- Never restart `lorekeeper web` or kill a generate process while a run is active: check `/api/jobs` and **abort** if anything is running, queued or stopping. CLI and Studio runs share one Ollama.
- Commits and releases: pull requests are squash-merged and the PR title is the commit message, in Conventional Commits form (`feat:`, `fix:`, `docs:`...). Never add `Co-authored-by`, "Generated with" or any other attribution trailer to commits, PR bodies or templates. release-please keeps a release PR open on `main` (version in `pyproject.toml`, `CHANGELOG.md`); merging it tags `vX.Y.Z`, which publishes `ghcr.io/nightspine/lorekeeper` (`latest`, `X.Y.Z`, `X.Y`, `edge` for main, `sha-` tags). See RELEASING.md.
- Schemas in `schema/` are normative and versioned with the spec (`"lorekeeper": "0.1"`). Keep the schemas, SPEC.md and the code in agreement in the same change.
