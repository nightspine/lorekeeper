# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Lorekeeper is a draft open standard (SPEC.md) for spoiler-gated book indexes ("X-Ray"-style companions), plus a Python reference implementation. The spec is the product; the Python code exists to make the spec testable and to serve later as the basis for a self-hosted server and generator. Reader apps (KOReader, iOS readers) are meant to consume indexes without any AI.

## Commands

```sh
uv sync                                   # install (Python ≥3.11, deps: jsonschema; dev: pytest)
uv run pytest                             # all tests
uv run pytest tests/test_gating.py::test_cross_book_replacement   # one test
uv run lorekeeper conformance             # run conformance cases
uv run lorekeeper conformance --update    # regenerate expected views after an intended gating change
uv run lorekeeper validate examples/sherlock-holmes/study-in-scarlet.json examples/sherlock-holmes/sign-of-four.json --series examples/sherlock-holmes/series.json
uv run lorekeeper validate examples/sherlock-holmes/study-in-scarlet.json --epub corpus/pg244/pg244.epub   # + anchor & quote checks
uv run lorekeeper blocks corpus/pg244/pg244.epub --start 100 --end 150    # list blocks (seq, spine, words, fp, text) for authoring
uv run lorekeeper fill-anchors INDEX --epub EPUB --write                  # compute fp from seq hints, record edition hashes
uv run lorekeeper toc corpus/pg244/pg244.epub                             # TOC positions for --chapters, beside the book's own "Chapter N" (chapters.py)
uv run lorekeeper generate corpus/pg244/pg244.epub -o out.lore.json --chapters 5-6   # needs Ollama running
uv run lorekeeper generate ... --resume                                   # continue an interrupted run
uv run lorekeeper generate ... --provider gemini --model gemini-2.5-flash # bring your own key: claude|openai|gemini|openrouter|mistral|groq|xai|deepseek|custom (key from the env var, or --api-key-file PATH; --base-url for custom)
uv run lorekeeper profiles INDEX... --tidy                                # older indexes: drop description-entities, backfill profiles (Claude; backups first)
uv run --extra claude lorekeeper portraits INDEX...                        # rewrite profiles from every passage mentioning each entity (Haiku; --prior earlier books; backups first)
uv run lorekeeper illustrate INDEX... --epub EPUB... --style ink --level main --provider gemini --quality draft --cap 3   # chapter pictures and portraits into art/<textHash>/<style>/ beside the index (resumable; --level main|all|none, none = portraits only; --portraits main|all|none, main by default; --limit N, --chapters 4-6, --prior INDEX for earlier series books; a model per job: --writer, --portrait-writer, --picker PROVIDER[:MODEL] for the scene prompts, the portrait/place/thing prompts and the choosing calls, --portrait-model [PROVIDER:]MODEL for the portrait image model; portrait prompts default to the text provider's strong model, the rest to --text-model else its cheap one)
uv run python bench/model_bakeoff.py MODEL...                             # compare Ollama models on one passage
uv run --extra claude lorekeeper arcs INDEX...                             # write a short per-book arc for each main character from the index's events (cheap model; --prior earlier books, --redo; backups first)
uv run --extra claude python bench/ask_eval.py INDEX... --series S --book B --at 0.33 --provider claude --model claude-haiku-5-5 [--fresh] [--roster N] QUESTION...   # try Ask on an index at a position; prints slice size, picks, answer, cost
uv run --extra web --extra claude lorekeeper web                          # Library, Reader, Runs UI on :8765
uv run lorekeeper web --no-auth                                        # skip the web app sign-in (trusted local use only; or env LOREKEEPER_AUTH=off)
uv run lorekeeper reset-password [--data DIR]                             # new generated admin password, printed once; forces a change and ends all sessions
uv run lorekeeper web --api-token TOKEN                                # require a bearer token on /v0 (or --api-token-file PATH, or env LOREKEEPER_API_TOKEN)
uv run lorekeeper docs export build/                                      # landing page (site/) + docs + spec + styles, for hosting
uv run lorekeeper share INDEX --epub EPUB -o bundle.json                  # a share bundle: scrubbed index + builder attestations (--series for a series book)
uv run lorekeeper registry add bundle.json --publisher NAME --source DIR  # check and file a bundle in a registry tree (check: same, writes nothing; remove ID --reason TEXT)
uv run lorekeeper registry build DIR -o build/registry --base-path /lorekeeper-registry   # the static registry: lookup files per edition, listings, indexes
docker compose up -d                                       # same server in a container on :8765, data in the lorekeeper-data volume (env: LOREKEEPER_DATA/HOST/PORT/OLLAMA_URL/API_TOKEN)

uv run python bench/compare_handwritten.py out.lore.json                  # generated vs hand-written example
```

The generator needs a local Ollama (`brew services start ollama`), or a cloud provider with your own key (every provider in `llm.PROVIDERS`: `llm.OpenAICompatible` serves all but Claude, which uses the anthropic SDK). Default model is `gemma4:12b-it-qat`; `qwen3.5:9b-q4_K_M` is the faster alternative. Thinking mode is deliberately off. A two-chapter run takes tens of minutes on a 16 GB M4, so run it in the background. Tests use a scripted fake model (`tests/test_generate.py`) and never call Ollama.

`corpus/` is gitignored; the README lists the download commands (pg244, pg2097, pg345 and the Standard Ebooks Scarlet). `examples/dracula/dracula.json` is a complete generated index of pg345 that the Library, the Docker image and the landing-page demo ship with; it must pass `lorekeeper validate --epub corpus/pg345/pg345.epub`, and `bench/site_demo_data.py` flattens it for the site. Tests that need a corpus EPUB skip when it is missing, so a green run without the corpus doesn't cover anchor resolution or quote checks.

## Architecture

The pipeline, in spec order:

1. **Text model** (`epub.py`, SPEC §3.1): EPUB spine → paragraph-level blocks → `seq` numbers. Standard library only (zipfile, ElementTree, html.parser). A document with no `p`-style blocks but real text (Calibre's `<div class="p">` paragraphs) is re-parsed with `div`/`blockquote`/`section`/`article`/`aside` as blocks (`FALLBACK_BLOCK_TAGS`, §3.1 rule 6); it only ever applies per document, so books that already parse keep their seqs and text hashes.
2. **Normalization and fingerprints** (`text.py`, §3.2–3.4): `words()` and `fingerprint()` are the cross-language contract. Every port (Lua, Swift, Kotlin) must produce identical output. Any change here changes every anchor in every index: run `fill-anchors` on the examples and update SPEC §3.2.
3. **Anchor resolution** (`anchors.py`, §3.6–3.7): the client side. It maps a reader's own edition onto an index's ordered anchors. Unresolved anchors take the *next* resolved anchor's location, so mismatched editions can only under-reveal. Keep that invariant.
3b. **Locators** (`locators.py`, §3.7): `locate(book, locator)` turns what a reader app holds (`{"block"}`, `{"cfi"}`, `{"xpointer"}`, `{"spine","word"}`, `{"spine","progress"}`) into the seq of the block it points into, rounding to the *preceding* block when in doubt (-1 before the first block; `exact=False` when a fallback decided), and `position(..., inclusive=)` gives the current anchor in the two modes: "finished" (the current block does not count, for views) and inclusive ("who is this on my page?"). `web/position.py` (Book Orbit) is built on it. Cross-language vectors live in `conformance/locators/` (run by `lorekeeper conformance`; skipped when the corpus EPUB is missing).
4. **Gating** (`gating.py`, §7): `view(indexes, Position, series, order, finished)` is the normative algorithm. Its output shape is `schema/view.schema.json` and is what `conformance/*.json` freezes.
5. **Generation** (`generate.py`, `llm.py`): `llm.PROVIDERS` is the one table of cloud providers (label, kind `anthropic`/`openai`, base URL, key env var, key URL, preset models with prices and a `cheap`/`strong` tier); it is the only place to update text model ids and prices (image models and their per-picture prices are in `llm.IMAGE_PROVIDERS`, below), and a stale preset never blocks anything because the UI also lists live models from `GET {base_url}/models`. `llm.make(provider, model, api_key, base_url)` dispatches on it. Pictures have a second table, `llm.IMAGE_PROVIDERS` (Gemini and OpenAI only, the only place for image model ids and prices, which are per quality level and where published per shape, `None` = "price unknown"; label and key variable come from `PROVIDERS` via `image_spec`; `image_price`, and `make_image` which dispatches on it and raises `ValueError("Claude cannot draw")` for Claude), whose backends live in `images.py`: one `draw(prompt, shape=, quality=, references=)` returning `Drawn` (bytes as the provider sent them, mime, cost), at most 6 reference pictures sent before the prompt, a safety refusal as `ImageRefused` with the provider's wording; `lorekeeper draw` tries a prompt. `OpenAICompatible` is stdlib-only: json_schema first, plain json_object with the schema in the prompt after a 400, and it adapts to models that reject `max_tokens` or `temperature` on the first 400; unpriced models cost 0 in `Usage` and show "price unknown" in the UI, never a made-up number. It reads chapters (from the EPUB table of contents, `epub.read`) in chunks of whole blocks. Per chunk: one extraction call, a rephrase call if a claim copies 9+ words of the book, one support-check call. Facets describe what an entity *is* (role, look, nature, allegiances, status); plot goes to events. The extraction also returns **profiles**, for every new person, creature and group and for anything it learns something lasting about (a new entity's one-sentence `desc` reads like the first line of a character sheet and, when the response has no profile for that entity, is committed as its first profile instead of a plain fact; with a profile it is dropped as a duplicate): a self-contained "who this is now" for entities whose picture changed, committed as `kind: "profile"` facets that replace the entity's current profile, including one inherited from an earlier series book, so a character keeps one growing description (the Reader shows the latest visible one). Those extraction profiles are pieced together one passage at a time; `portraits.py` rewrites them afterwards the way a reader would: at each chapter end, for every entity mentioned at least 2 times (rewritten once at 4 mentions if the first came from fewer, then again once mentions grow by half, and at the next chapter end after a checked fact records a change in standing, `portraits.STATUS`: died, married, captured, revealed...; a thin tie or role is stated plainly), it sends the paragraphs around every mention so far (up to 40, sampled evenly, first and last kept, with up to half of them given to the mentions since the previous description and kept first under the budget, still sent in reading order; a name counts only if no other entity shares it, so "Harry" but not "Potter") together with the entity's last 8 checked facts, and asks for a character-sheet description, not a plot summary, whose first sentence states any lasting change in standing the passages show ("Dead, killed by..."); a change in standing recorded since the last portrait, as a checked fact or as a turning point naming the entity ("Lucy dies"; `changes_standing`, which ignores hedged phrases such as "near death" or "fears she is dead", `HEDGED`), is quoted in the prompt, the portrait is never revealed before it, and one whose first sentence does not state it (a death needs a death word, `DEATH`; "engaged" does not count) gets one rewrite ("rewritten: change in standing"); a rewrite may not drop a death the previous portrait opened with, but only when the companion records that death: code finds the candidates, the entity's checked facts and the turning points naming it up to the mark whose text has a `DEATH` word (`deaths_of`; `opens_with_death` prefilters the previous description's first sentence the same way), and only when the first sentence and at least one candidate have one does a cheap choosing call (`DEATHS`, `DEATHS_SYSTEM`, `DEATHS_SCHEMA` = `{"dead": [int]}`, `own_deaths`, batches of `DEATH_BATCH` = 40) answer which numbered items state that this entity itself died or is dead (not someone else, not hedged, not figurative: "hunter of the Dead", "Her mother died"); code uses only the numbers, cached per (entity id, text), and the rule applies when the call confirms both the opening and a recorded item. A failed call, or a reply with no list of numbers (a refusal or cut-off reply, `{}`), caches nothing and keeps the opening. A rewrite also keeps the looks the previous description of this book stated (the last portrait, else the latest extraction profile at or before the mark; never an earlier series book's): code cuts it into pieces at sentence ends, punctuation and joining words (`_pieces`), one cheap call (`LOOKS`, numbers only, cached per description text) picks the lasting-look pieces, of which `MAX_LOOKS` = 12 are kept ("looks over the cap" counts the rest), and the prompt lists them to keep unless the passages show a change, which the reply names in `changed` (`LOOK_SCHEMA`; a changed piece counts as kept if the new text shares a content word with it). `lost_looks` flags a piece when more than a third of its content words are missing (endings allowed, `ask.STOP` ignored, no list of look words), and a second cheap call (`LOST`, `confirm_lost`, the flagged pieces numbered 1..n) can clear a flag, never add one ("kept: look in other words"). A look kept from an extraction profile moves the reveal point to that profile's anchor or later. One gate (`faults`) checks the lost standing and the lost looks on every candidate text, whichever rewrite made it: one rewrite naming every fault ("rewritten: kept a stated look", "rewritten: kept the change in standing"), else the previous portrait stands ("dropped: lost the change in standing", "dropped: lost a stated look"). Only text up to that point is sent and the portrait is revealed at the first anchor after the last paragraph used. A portrait naming a word the book hasn't used yet (model memory) is dropped; "now"-style wording gets one rewrite. A profile, desc or portrait that states a tie (wife, fiancée, mother, heir: `generate.TIE_WORDS`) the passage or the entity's notes never use is dropped ("dropped: tie not in the text"; portraits get one rewrite first, and for them the sampled passages, the entity's checked notes and profiles up to that point and the previous portrait all count as support), because models upgrade "someone Harker keeps notes for" to "Harker's fiancée" from memory. Portraits replace extraction profiles from their first one's reveal point on (one at that same anchor goes too); earlier ones stay as the early description, and a rewrite that lands on the previous portrait's anchor stands in for it rather than sitting beside it. Every finished web run writes them as a "Writing descriptions" stage (`JobManager._portraits`: the cheap model of the run's own cloud provider, else of the first configured one, about $0.89 on a long novel on Haiku (Empire of the Vampire, 2,062 calls, 45 of them death calls), skipped without any cloud key; a failure there keeps the index as the run wrote it). `arcs.py` then writes each person, creature and group a short **arc** per book, `kind: "arc"` facets (1 to 3 sentences, at most 400 characters, about this book only; SPEC §4.2, limit §6.3, view rule §7.3.5), from the index's checked events and not the book text: at each chapter end an entity gets one when it is named by 2 non-minor events or a turning point and has none yet, then again after a turning point or 2 more non-minor events name it; the prompt holds its latest profile as context, its events up to that point, its ties and its previous arc, the portrait checks run with a 400 limit (unknown names, hindsight wording, unsupported ties) plus a sentence count, `ABOUT_THE_TEXT`, no chapter references (`CHAPTER_REF`) and, with the EPUB, the 8-word copy rule, with one rewrite then a drop, `from` is the anchor of the latest event the writer was given (never before the entity, a name it uses or the arc it replaces; SPEC §4.2 only requires it at or after the latest event the arc tells), the reply names which events it tells (`told`; a reply without a valid list gets the one rewrite, then every event sent counts as told), `evidence` is exactly the union of the told events' evidence and `replaces` the same book's previous arc. It runs as the stage after "Writing descriptions" and the reapplied edits (`JobManager._arcs`, same cheap model, skipped for a local run and without a cloud key, a failure keeps the index), and `lorekeeper arcs` backfills older indexes. A kin or role word is never a person: a proposed person or added name that is only such a word once a leading article, possessive pronoun or plain adjective is taken off (`bare_kin_word`, `BARE_WORDS`: "Father", "Mama", "the boy", "my mother") is dropped ("dropped: kin or role word, not a name"), while a kin word with a proper name ("Uncle Vernon", "Father Brown", "Mother Superior") or with the name in a note ("Mama (Auriél)") is a real name ("Big Brother", "The Stranger" and "Porter" are names too: only kin words and boy/girl/man/woman/lad/lass/child/baby are bare; the loss of books whose protagonists are only "the man" or "Ma" is accepted, since vague kin words becoming people was the complaint), as is a name in a note after a bare outer ("the boy (Harry)"). A possessive kin description ("Gabriel's sister", `kin_description`) resolves to the one named entity the companion already ties to Gabriel that way, from this book's ties or an earlier book's (`kin_ties`: "sister of" either way round, a sexed word excluding the other sex, modifiers agreeing: an unmodified "father" never matches "stepfather of", "elder sister" never "younger sister of"; stat "kin descriptions matched to a known relative"), is dropped when several fit ("dropped: kin description fits several") or when its owner is not a known named entity ("dropped: unnamed relative of no one known"), and otherwise, like any description ("the old priest"), becomes an entity only if the same reply gives it a part in an update, tie or event ("dropped: unnamed relative with no part"). When a tie makes exactly one named person that kin of X and exactly one such description exists, the named entity is folded into the description at the end of the part, so the description's id stays and no id names someone the reader has not reached (`_fold_kin_descriptions`, "merged: kin description into the named relative"), but only if the person is this book's own, the identifying tie was revealed at or before their first appearance (a tie stated chapters later would give a twist away), the description's notes do not keep the identity back and no turning point names both (`hidden_identity`); `profiles --tidy` does the same to older indexes and removes person entries named only by kin or role words. Names must appear in the passage (a name the model knows from elsewhere is dropped: it could name someone before the text does); a new entity is introduced at the first verbatim use of its name in the indexed text (`earliest_mention`), never later than needed; people named together ("Mr. and Mrs. X") are split into two (`split_couple`); matching (`match_known`) respects titles (Mr/Mrs never match), plural and reordered forms, a full name for someone known only by title and surname, a tail form ("Van Helsing" / "Abraham Van Helsing") and middle names or initials (`merge.same_person_name`). A proposed name goes through `resolve_name`: when it fits two or more known people (`ambiguous`), it never creates a third entity; if the hits all match each other by name and nothing forbids it (`_may_merge`: no `Options.distinct` pair, no relation between them, no title of another sex, no two different full proper names) they are folded into one in-run (`_merge_entities`, logged in `added` as kind "merge", stat "merged by a bridging name"); otherwise a small `DISAMBIGUATE` call over the three paragraphs around the name picks one, "both" or "none" (at most `MAX_DISAMBIGUATE` per chunk), as it does for a new bare first name while a person known only by title and surname is in the passage. The model's `names` list is not trusted: each entry is a (name) claim in the fact-check, a name already carried by another entity is never added to a second one, and a bare family surname is never a name, and a person never takes a name the text gives a relative (`names_a_relative`: "her mother Mrs. Westenra", "daughter of Mrs. Westenra" in the cited paragraphs or the entity's notes) or, for a titled name, one any sentence read so far uses beside the entity's own name as a second person (`names_two_people`: "Mrs. Westenra was anxious concerning Lucy"), stat "dropped: name of a relative". `earliest_mention` searches a titled name only in its exact form ("Mrs. Harker" must not inherit chapter one from "Jonathan Harker"). The fact-check (`VERIFY`, optionally a stronger `Options.check_llm`) gives every claim a verdict with a one-line reason: `unsupported` drops it (kept with its reason under `rejected` in the `.report`), `unsure` keeps it but lists it under `unsure` (stat "kept: checker unsure"), and a claim with no verdict is accepted; it sees earlier chapter recaps for recap claims and moves facts that narrate a moment into events, except descriptions (`DESCRIPTIVE`, "A tall man in black who..."), which stay facts. Events are every development that changes the situation, up to `max(6, words/200)` per chunk, each weighed by the model as `turn` (a turning point: revelation, twist, reversal, realization, death, a decision with no way back), `plot` (an ordinary development, stored as no `kind`) or `minor` (a small moment; `EVENT_KINDS`, SPEC §4.4), and the prompt names the chapter the passage is from. Each event may carry a `setting` (where it happens, as the book states it, fact-checked like a claim and linked to a known place entity); the Timeline groups a chapter's events into scene runs headed by the setting and the position panel shows the last known setting in the current chapter. The chapter summary asks for complete sentences on what the passage does to the story, leaving out scenery, meals and travel details; a summary sentence or event under `MIN_SENTENCE_WORDS` words (a heading or a label such as "unresolved") is dropped ("dropped: not a sentence"); a chunk whose summary comes back empty gets a chapter recap made of its own checked events, minor ones left out ("chapter recap from events"). The context block lists each mentioned entity's existing ties (`_ties`), and the prompt asks for a relation only when the companion lacks it or the passage changes it. A relation is a lasting tie, never one action, with a `kind` (`RELATION_KINDS`: family, romance, friendship, alliance, service, hostility, acquaintance, place; SPEC §4.3): a label over `MAX_TIE_WORDS` is dropped ("dropped: not a tie"), a passage keeps one tie per pair and kind, the one shown latest ("dropped: second tie for a pair"), the fact-check lists ties that narrate one action under `moments` and they are dropped ("dropped: an action, not a tie"), and a new tie of the same kind between the same two `replaces` the current one (`_current_tie`, "ties replaced by a newer one"), so "fiancée of" becomes history when "wife of" arrives. The story recap walks the whole arc so far and then the recent stretch (up to 10 sentences); a recap or summary that talks about "this passage" is dropped (`ABOUT_THE_TEXT`) and the previous one stays. Chunk size defaults to `default_chunk_words(provider)`: 8,000 words (about a chapter) for a cloud provider, 2,500 for Ollama; the build form and the CLI follow the provider unless a size was chosen. `Options.chunk_mode` `"chapter"` (CLI `--parts words|chapter`, default per provider, `--whole-chapters` kept as an alias for `--parts chapter`; job config `chunk_mode`, the build form's "Read whole chapters"; on by default for a cloud provider and off for Ollama in the form and the CLI (`default_chunk_mode`), while a job config with no `chunk_mode` means words; an explicit `--chunk-words` alone means words, `--resume` keeps the mode recorded in `.state`; the form follows the provider unless the person chose) makes a part a whole chapter whatever its length, so there is one call and one chapter recap per chapter and the prompt calls the passage "the whole of <chapter>". A chapter over `max_part_words` (`MAX_PART_WORDS` = 20,000 words for a cloud provider; `max(1500, (num_ctx - 4096 - 3000) × 0.7)` words for Ollama, never above the cloud cap) is cut at a scene break in the last 40% of the words so far (`is_scene_break`: a short heading-like block only; `epub.py` drops wordless blocks, so `* * *` rows never reach it), else at the paragraph where the cap is reached. If a reply is cut off (every provider) the part is split in two and each half is read again. Each part after the first, the first part of a chapter included, gets a "Where the previous part left off:" bridge (the last two blocks, at most 150 words) as context only: no claim may cite it and the fact-check is told so. The Claude backend sends no sampling parameters (the API rejects `temperature` since 2026-10-21); Ollama and OpenAI-compatible backends use 0. Proposed names pass `triage_name` first: possessive descriptions of things ("Gabriel's fear") are dropped, descriptions wrapped around a name ("Celene's brother Gabriel", "Chevalier of the Golden Host (Gabriel)") resolve to that entity; unnamed people ("Gabriel's daughter") stay. The extraction also returns a story-so-far recap and a list of summary sentences; each sentence is fact-checked on its own and the survivors become a `scope: "chapter"` recap (one per chunk, titled with the chapter, so a long chapter has several parts the Reader joins). The model only proposes content. Python assigns anchors, ids and reveal points: `from` = the last cited block, then snapped *forward* to the next anchor-eligible block (≥ 6 words, unique fingerprint). Python also matches names (`match_known`, `mentioned`: exact, without honorifics, or a unique surname) and drops anything that fails a check. The index and a `.state` sidecar are written after every chunk, which is how `--resume` works. A `.report` sidecar holds drop counts by reason.
6. **Web UI** (`web/`, optional `web` extra): FastAPI app (`app.py`) plus `jobs.py`: a content-addressed book store and a single-worker job queue (one Ollama model at a time) that persists job metadata and an events JSONL under `lorekeeper-data/`. It streams events to the browser over SSE. The frontend is no-build vanilla ES modules in `web/static/`. Its stylesheet is split per area (`css/base.css` holds the tokens, the shell and the shared primitives; `library.css`, `reader.css`, `graph.css`, `studio.css`, `settings.css`, `auth.css` own their pages, and `read.css`, after `reader.css`, the reading view), so parallel edits don't collide. The design is "lit and unlit" (what you've read is lit, what's ahead is dark), laid out as a workbench (direction A; every page is converted). Surfaces are flat: two grounds, `--bg` for the page and `--pane` for the rail and side panes (`--pane-2` for a lifted row or the selected tab), divided by hairlines (`--line`, `--line-2`); no glass, no lit top edge, no shadow on anything in the page (floating things keep one: dialogs, the palette, toasts, the entry drawer); a `.card` is a region on a hairline, not a box. One beacon accent (links, "complete", the primary button as solid beacon), ember for anything new or in progress, rose for danger, Manrope only (JetBrains Mono only in the run log), 6px radius on controls and 0 on panes, 13px body, 12px labels and 18px page titles in the app (the scale is set on `html.lk-app`, so the docs site and landing page, which load the same base.css, keep their reading sizes), dark as the default theme with a daylight variant under `data-theme="light"` (body text, `--text-3`, `--beacon`, `--ember`, `--rose` and the type colours pass 4.5:1 on `--bg`, `--pane`, `--pane-2` and the selected-row tint in both themes). Use the tokens in base.css (`--bg --pane --pane-2 --hover --sel --line --line-2 --field --text --text-2 --text-3 --beacon --ember --rose --shadow --t-*`); the older names still used by a few area rules and the docs site (`--glass`, `--glass-2`, `--edge`, `--edge-lit`, `--track`, `--surface`, `--shadow-2`, `--t-*-soft`) are defined in the flat values, not for new code. Shared primitives are styled once in base.css: `.btn` (32px), `.input`/`.select` (32px), `table.data` (34px header, 46px rows, hairlines, tabular numbers, `tr.selected` tinted), `.view-tabs` (the selected tab on `--pane-2` with a hairline ring), notices, toasts, dialogs. The first start with no users creates it with `LOREKEEPER_ADMIN_PASSWORD` when set, else `secrets.token_urlsafe(12)`, prints it once, and sets `mustChangePassword` in both cases. While that flag is set every protected route except `/api/auth/*` answers 403 `{"detail", "code": "password-change-required"}`, enforced server-side. Store: `lorekeeper-data/auth.json` (0600, atomic write like `secrets.py`): `users.<name>` = `{hash, mustChangePassword, created, changed}` and `sessions.<sha256 hex of token>` = `{user, created, seen}`. Hash: stdlib `hashlib.scrypt` n=2**15, r=8, p=3, 16-byte salt, stored as `scrypt$32768$8$3$<salt>$<hash>` (base64url) so parameters can change; compared with `hmac.compare_digest`; an unknown username still runs one scrypt. Policy: 12 to 128 characters, no composition rules, must differ from the current one. Sessions: cookie `lorekeeper_session` (`token_urlsafe(32)`, only its sha256 is stored), 30 days idle (`seen` refreshed at most hourly) and 90 days absolute, HttpOnly, SameSite=Lax, Path=/, `Secure` when `request.url.scheme` or `X-Forwarded-Proto` is https; changing the password deletes every other session and rotates the current one, `reset-password` deletes all. 7. **Library catalog** (`web/catalog.py`, `web/bookorbit.py`): the Library browses **books**, and index files are *versions* of a book. A version is matched to a book by its edition text hash, so it needs the book's EPUB on disk. Book Orbit books are a synced cache (`lorekeeper-data/bookorbit/books.json`) holding only books with an EPUB (comics and PDFs have no text to index), plus per-library counts. After signing in the user picks which Book Orbit libraries to show (`bookorbitLibraries` in `library.json`; absent means all, and a new connection clears it); `Catalog.bookorbit_books()` applies both filters. Their EPUB is downloaded on first build (`prepare`) and linked in `library.json`, which also holds each book's default version and manual series for uploads. Series come from Book Orbit, from EPUB metadata (`epub.read`: EPUB 3 `belongs-to-collection`, then Calibre's series meta), or from the user, and are grouped by slugged name. `preflight` reports earlier books with no index and numbering gaps (`notInLibrary`). Builds that go through the catalog get `series_id`/`book_key`, a written series manifest, and `prior` = earlier books' default indexes (`Generator._load_prior` / `_localize`: returning entities keep their ids, cross-book `replaces`, the story-so-far carries over). Front and back matter is decided once, server-side (`web/jobs.py` `NOT_STORY` / `is_story`; a cast list such as "Dramatis Personae" is front matter). Chapter numbers are the book's own (`chapters.py`: `classify` a title as `chapter`, `divider` (Part/Book/Volume/Section/Act), `named` (prologue, interlude, front and back matter, a play's scene) or `other`; `own_number` reads "Chapter III", "Two", "I: Title", "3 - Title"; `numbering` over the whole toc with story flags gives `{kind, number}`, the stated numbers when more than half the story chapters state one, else a count that skips dividers, named and non-story sections; vectors shared with `js/chapters.js` in `tests/fixtures/chapter_numbering.json`): `/api/editions/{hash}` and `/read/toc` chapters, the estimate's `chapters` rows and the mentions rows carry `number` (null: the title alone), never a position among listed rows. A run that covers every story section is marked complete (`Options.whole_story`). Book Orbit auth is username/password with `clientKind: "native"`. Only the rotating refresh token is stored (in secrets), never the password. The access token is in memory and refreshed on 401 or expiry. Lorekeeper never writes to Book Orbit: `BookOrbit._call` refuses every non-GET except the `/books/query` read before any request is made (tested), and the Reader never pushes a position back. In the Reader, a Book Orbit book the person marked read there (`finished: true` in the position reply, from its `readStatus`; `rereading`, `abandoned` and the rest do not count) opens at the end with no spoiler line, no "Show me anyway" and the source line "Finished in Book Orbit" (the Reading list says "Finished", and a Library row, its pane and the phone sheet say so too), and any other Book Orbit book that isn't finished treats the synced position as a spoiler line: the slider stops there while dragging, and any deliberate move past it (release, percent, chapter jump, next reveal) asks first (`moveTo`); "Show me anyway" allows it for that session and the source line says so, "Back to Book Orbit's position" clears it. `GET /api/library/{key}/position` (read-only) reads the user's Book Orbit reading progress for the book that owns that index (`BookOrbit.progress`: newer servers answer `GET /reading-progress?bookId=`, older ones only `GET /books/{id}/progress`, a flat row per file, normalized to the same shape) and returns `{synced, source, finished, updatedAt, percentage, basis, seq, p}` (a book Book Orbit has marked `read` answers `finished: true`, `basis: "finished"`, `p` 1, so the whole book counts as read and `seq`, the last block, is informational, even with no progress rows; the status is read live from `GET /books/{id}`, falling back to the last live status seen, then to the sync cache), or `{synced: false, reason}` (`not-bookorbit`, `not-connected`, `no-edition`, `unreachable`, `no-progress`) so the Reader degrades quietly; `p` is the fraction of words before block `seq`, so the block being read never counts as read. `web/position.py` `resolve` picks the first usable of EPUB CFI (the id asserted on the target element, else the character position inside the XHTML), Kobo (spine file plus percent), KOReader XPointer and the whole-book percentage, using each `epub.Doc`'s `spine_child_index` because CFI and KOReader spine steps count `linear="no"` items too; an exact position more than 5 points away from the percentage is stale (another device moved on) and the percentage wins, and it never raises.
8. **Entity identity** (`merge.py`, `web/identity.py`): one set of name rules (`core`, `extends`: titles stripped, parenthetical notes and possessive descriptions ignored, a shorter prefix form counts for people only) is shared by `Generator.match_known` and duplicate detection. `candidates` groups matching entities across a series: groups where everyone matches everyone are `sure`, others are offered pair by pair. `merge` folds one id into another in every index of the series. It is spoiler-safe because names and facets keep their own `from`, except for hidden identities ("the stranger" is Gabriel), which must never be merged. The web layer only rewrites generated indexes, refuses while a run writes one, snapshots files to `lorekeeper-data/merges/<id>/` for undo, and keeps "not the same" pairs in `library.json` (`distinct`). The Reader suggests a pair only when both entries are visible at the reader's position. Beyond name rules, a model reading short descriptions of the cast proposes pairs the names can't show ("Mr. Dursley" / "Uncle Vernon", `merge.propose`, Haiku). Every pair, proposed or by name, is then judged (`merge.judge`, Sonnet 5.5 when a Claude key exists, else the same model as propose; `judge_model` / `strong_judge_model` in `web/app.py`) from the whole entry of each side (full latest profile, up to 8 details, up to 8 ties as sentences, where it is introduced), the paragraph where the later entry's name first occurs in the book with one paragraph either side (EPUB found by the index's `editions[].textHash`; judged without it when the EPUB is missing), and any paragraph where both names occur as separate mentions. The verdict (`same`, `different`, `unsure`) comes with a one-line `because` that is stored (state `because`, and the merge journal) but never shown to readers, since it may state whole-book facts. A pair left `unsure` without the text is judged once more when the EPUB is on disk. Bump `merge.JUDGE_VERSION` when the prompt changes. Policy (`identity.auto_ok`, `Identity.auto_merge`), all as one undoable step after each check: judged `same` merges automatically when the pair is a same or fuller name, a shared alias where at least one shared name is a proper name (`merge.proper_name`: "Aaron", "Van Helsing", not "the Professor", "the stranger", "Forever King"), or a model-proposed pair whose names are all proper names. Shared descriptors only (the shape of a hidden identity) always go to review. `different` pairs are stored and not listed. `unsure` pairs are listed as "Couldn't tell from the text". In a group where an entry fits several others ("Chloe" fits two Chloes) a pair is merged only if neither entry is in another live suggestion. Family surnames and bare titles are not evidence of identity (`merge.family_names`). Display names (`merge.rank_names`) prefer an entity's actual name over titles: a title word anywhere marks a title ("Forever King"), a shared family surname marks a real name ("Fabién Voss"); the generator applies the same ranking when a new name arrives. Measured on real books on 2026-10-28: the Empire of the Vampire series went from 137 listed pairs to 17 for review, and a fresh Dracula build leaves none.

Nobody types an anchor: an op names a paragraph `seq`, and `_Ctx.anchor` snaps forward to the first block with 6+ words and a unique fingerprint, reusing an existing anchor or minting one in the generator's id scheme; `coverage.through` moves forward to it when needed, an entity's `from` is always its earliest name's. `GET /api/editions/{hash}/blocks?seq=&before=&after=` feeds the paragraph picker (`eligible` says whether a block can carry an anchor). Entity-wide ops (`set-type`, `delete-entity`) reach every index of the series; item edits only the book that holds the item. Arcs are read-only (a summary of many events: `add-facet` with kind `arc`, `edit-facet` and `delete-facet` on one answer 400; nothing rewrites an arc after a hand edit, so change the events and the next build writes it again after edits are reapplied, or run `lorekeeper arcs --redo`). Text goes through `check_wording`: the spec's length limits, `generate.HINDSIGHT`, `MOMENTARY` for descriptions only, `unsupported_tie` against the cited paragraph and its neighbours, and the 9-word copy rule (both only with the EPUB on disk); a refusal is a 422 with `code: "wording"` that the form shows under the field. Each edit is also recorded in `lorekeeper-data/edits/<textHash>.json` with its journal id and a target (entity id, item id, original text), undo removes it again, and `JobManager.after_run` (`Editor.reapply`) puts them back on every new build of the same edition: by id when it survived, else by the entity and the original text, skipping what no longer applies ("your edits: 5 applied again, 1 no longer apply" in the run log). An edited index is still a plain SPEC 0.1 document: the only trace in the file is `provenance.updated` and a contributor with role `editor` (`author` for a hand-made one).
8c. **Registries** (`registry.py`, SPEC §8.7, `schema/listing.schema.json`, `schema/share.schema.json`): how an index is shared. Nothing about the index document changes. `lorekeeper share` makes a bundle (the index with every edition's `label` and `fileHash` scrubbed, the series manifest for a series book, optional `derivedFrom`, and builder attestations when the EPUB is given: `book-checks` from `check_against_book` and `spoiler-gate`, which counts names whose `from` anchor comes before the book's first verbatim use of the name). A registry is a tree of files (`indexes/<publisher>/<slug>/listing.json`, immutable `v<N>.lore.json`, `series.json`, plus `removed.json`); `registry check`/`add` treat a bundle as hostile input, since they run in the registry repository's GitHub Action with write access: paths come only from the validated publisher and the computed slug, the 5 MB cap applies before parsing and again to what would be stored, nesting past 32 levels, NaN/Infinity, lone surrogates and non-ASCII or non-UTC timestamps are refused, and every refusal is a finding, never a traceback. Licences are CC0-1.0 or CC-BY-4.0 only. A series is shared as a set under one publisher: a later book `requires` the earlier listings, a new version of an earlier book may not break the later ones, and `remove` refuses a listing others require unless `--with-dependents`. Attestations say who vouches (`registry`, `builder`, `reader`); builder and reader ones are self-reported and a client must show that, never one merged number. `registry build` writes the static profile deterministically (`.well-known/lorekeeper` with `static: true`, `v0/lookup/{text|isbn|gutenberg|openlibrary|wikidata}/<value>.json`, listings, byte-identical index copies); a static host cannot send the digest as `ETag`, so a client MUST verify fetched bytes against the lookup digest. The community registry is `nightspine/lorekeeper-registry` (served by GitHub Pages; its takedown policy is `TAKEDOWN.md` there). The app's side is 8d.
8d. **Community indexes** (`web/community.py`, `audit.py`, `web/static/js/community.js`): the app side of registries, off until the person opts in (`community` in `library.json`: `enabled` null = not asked, asked once on a build page; a lookup tells the registry which book you own). Only the server talks to the registry (default `https://nightspine.github.io/lorekeeper-registry`; https, or http to localhost), and everything it returns is untrusted: one 10 s deadline per fetch (the fetch runs in a thread whose sockets are shut when the deadline passes) that covers connecting, redirects (at most 3, each followed only under the registry's origin and path, like hrefs), headers and body, a 6 MB cap, the guarded parser from `registry.py`, a lookup checked as an envelope and then result by result (at most `MAX_RESULTS` = 200 considered, each stopped at its first schema error), hrefs confined to the registry's own origin and path, the digest verified on every fetched index, impossible attestation counts ignored, and one bad result or listing dropped rather than failing the response. A listing or index is fetched and installed only through an edition whose `textHash` is the reader's and which is the index's only `builtFrom: true` edition (two would let the Reader place anchors against another copy; `builtFrom` exactly true is the one meaning of "exact" in the Reader, `check_against_book` and here; a listing carries no `builtFrom`, so the check is on the index); fetch also refuses (422 `invalid`, nothing cached) an index with an anchor whose `seq` hint is not where its fingerprint resolves, an unresolved one included, since the Reader places anchors by seq on an exact edition (anchors without a `seq` are only reported); any refusal at fetch also removes the cached file and its audit; a fetch past its deadline has its sockets shut (a connection that comes up after it closes itself, `cancel`) and at most `MAX_INFLIGHT` = 4 run at once; a file name too long to store is refused, and `registry_slug` keeps a non-default port. This version offers exact-text matches only (a listing edition's `textHash` equals the EPUB's) and hides series listings. `GET /api/community/books/{catalogKey}` answers a state (`off`, `ask`, `no-edition`, `unreachable`, `ok`) and ranked results (complete first, no early names first, audits with a Wilson lower bound of supported/(supported+unsupported) at or above 0.5, then unaudited, then weak audits, then newer); the lookup is cached 10 minutes and served stale when the registry is down. Fetch stores the verified bytes in `community/cache/` (20 most recent kept) and runs `check_against_book` and `registry.spoiler_gate` against the EPUB; the preview is the Reader on that cached document (`#/preview/<digest>`), held at the end of chapter 3 with the `moveTo` confirm; install copies it to `community/indexes/<registry>--<publisher>--<slug>--v<N>.lore.json` (Library source `community`), read-only (edits and merges answer 409), never pinned as the default on a first install and ranked below anything built here on ties. Two measures are shown, each with who vouches: fit, and checked ("N of M claims held up" from an audit, M = supported + unsupported, with the unsure count as a second sentence, else "Anchors and quoting checked"); the headline says only "Whole book" or "Partial". `audit.audit(index, blocks, llm, n=50)` samples claims that cite a passage (non-profile facets, ties, events, at most a tenth chapter-recap sentences) evenly across the book and asks whether the passage states or clearly implies each (`supported`, `unsupported`, `unsure`); paragraphs are sent whole, a recap sentence gets the stretch its recap covers, `audit.estimate` prices a run from the real prompts, and the app offers an audit only with a cloud provider's strong model (409 `needs-cloud-model` otherwise). Sharing (`share/check`, `share/audit`, `share/bundle`) builds the bundle with `registry.make_bundle`; the dialog never shows book text (counts and item paths only), a stored audit is keyed to a hash of the audited content so a licence change keeps it, and `set-license` is not a hand edit. Submission is the registry repository's GitHub issue form, opened in a new tab.
8e. **Ask** (`ask.py`, `common_words.py`, `web/app.py` `GET /api/ask` and `POST /api/library/{key}/ask`, `web/static/js/ask.js`, docs `ask.html`): questions about the book answered from the index, the book's own text before the position, or both (`source` `index`|`both`|`book`; `index` is the old path, byte for byte). The route builds `gating.view` at the reader's anchor (with `finished` and `order`; the body may carry `book`, a mismatch with the index's series book is 422 `bad-position`), and `ask.select` picks what the model sees as plain text notes under a character budget (`DEFAULT_BUDGET`, a smaller `OLLAMA_BUDGET`): a header (book titles only when the view spans more than one book), the entries the question names (`merge` name rules, kin words followed through connections for follow-ups), their profiles, details, connections (capped per entry) and events oldest first, with the first and the last few put first in line, then chapter recaps found by word match (capped at a quarter of the budget). Chapter questions (`chapter_matches`: number or numeral, last/latest/this/current of the named book else the current one, previous, a written-out title) take the asked-for parts outside that cap, up to half the budget, shortened as needed; a book with no recaps gets a note, never another book's. With a cloud model (`roster_chars` = `ROSTER_CHARS`; 0 for Ollama) a question that names nobody first makes one pick call over `ask.roster`, and a who/whom/whose/which/where/called/name question about a named or carried entry with other content words makes one over `neighbours()` when it has any (ties and shared events). Ollama gets neither list, but still a names-only `_pick` when nobody is named and no words match. Measured on Haiku, on one 700-entry series: about 9,000 to 19,000 tokens and 0.1 to 0.2 cents for a question that names someone, about 0.6 cents with the roster pick; a small index sends far less.

**Book text** (`source` `both` or `book`): `ask.TextBook` (`book`, `title`, `blocks`, `chapters`, `numbers`, `before`) per book, and `ask.BookText(books)`, built once per question, keeps only blocks with `seq < before` (defence in depth: the route cuts first), with an in-memory BM25 index (`BM25_K1` 1.2, `BM25_B` 0.75, light `_stem`) and `vocab`, every word of the kept text. `BookText.search(terms, budget_chars)` grows each hit block into its neighbours in the same book and toc chapter up to `PASSAGE_WORDS` = 250 words (one longer paragraph is cut to the window with the most query words, `_window`), passages never overlap, under `MIN_SCORE` = 0.25 of the best score dropped, at most `MAX_PASSAGES` = 24, filled to the budget. The query (`_query`): the question's content words 1.0, a word written as a name that is no named entry's name 1.5 (`WRITTEN_NAME_WEIGHT`), the named entries' names and aliases 0.5 and carried ones 0.4 (low: a narrator's "I" and a main name are on every page), then the words of the `EXPAND_EVENTS` = 4 visible events sharing most of the question's plain words at 0.3, expansion from the gated view only. `_answer_text`: `select` gets `extra_vocab=bt.vocab`, so the unknown-word and unknown-name tests, the no-call refusal and history masking count the words before the frontier as met (a person only the book has named is not refused); "both" makes the same picks as index mode, "book" none; passages get up to `budget // 2` in "both" and `budget - 600` in "book", and the notes are selected again with what the passage block leaves ("book" sends no notes and accepts no note cites, its block opening with a header of books and where the person is). Passages go in story order inside `<passages>` (`_PDELIM` strips either delimiter from book text), tagged `[p:1]`, `[p:2]`… (`_TAG` matches them), and a passage cite is exactly `{kind: "passage", id: "p:<book or ''>:<seq>", book, seq, end, chapter, number}`. Prompts `SYSTEM_BOTH` and `SYSTEM_BOOK` (`SYSTEM` untouched): data not instructions, passages are the book's own text and everything read, use them for detail, some are beside the point, "the book" for a passage and "the index" for an entry, at most 8 words quoted in a row in quote marks. Not found is `NOT_SAID_BOOK` ("The book doesn't say, up to where you are.") or `NOT_SAID_BOTH` ("Neither the index nor the book says, up to where you are."); a "book" question with no passage gets it with no call (note "no passages"). Checks inside the one retry: the outside-knowledge vocab is the notes and passages as sent; the copy rule, `text.copied_runs` over `shingles` of the sent passages at `COPY_RUN` = 9, asks for own words, notes "rewritten: copied the book" and, still copying, gives the not-found text with "refused: copied the book"; "the passages" in the voice is caught (`_VOICE_TEXT`, rewritten to "the book"). `Answer` gains `source` and `passages`. History cites that are passage cites (`p:…`, `[p:…]`) are dropped in every source before anything else, and the route and `historyFor` drop them too. The route (`ask_text`, `index_book_file`) takes `source` (absent `index`, anything else 422 `bad-source`) and `p`, the Reader's word fraction (a number 0..1, not a bool, required unless `index`, else 422 `bad-position`); the book being read gives a `TextBook` of the blocks before `frontier_seq(book, p)` (the block holding word `floor(p × words)`, so the block being read never counts; `len(blocks)` at `p >= 1`; shared with `art_position`), with only the chapters starting before it and their `toc_numbers` rows; an earlier series book is added whole only when it is in `finished`, earlier in the order used and its index's `builtFrom` EPUB is here, books in reading order with the current one last; no book file is 409 `no-book-file` before any model call; the reply adds `source` only when it is not `index`. Measured on Haiku on Dracula and Empire of the Vampire at p = 0.5 (20 questions, `bench/ask_eval.py --epub --source all`): about 0.1 cents a question for index, 0.15 to 0.2 for both (0.3 with a retry), 0.1 to 0.2 for book; "both" gave the fuller, scene-level answer on 18 of 20; lexical search still misses a scene told in other words ("Kiss me!"). The frontend: a `.seg` choice "Index and book" / "Index only" / "Book only" (`SOURCES`, `SOURCE_LABEL`) at the top of the tab, shown only when `ctx.hasBook()` (`canRead()`) and a model is available (else the source is `index` and the tab is as before), remembered in `localStorage` `lk-ask-source` (`readSource`, default `both`), with one quiet line under it ("Passages of the book are sent to <company>." with Claude read as Anthropic, or "Passages of the book are read by the local model.", none for Index only); requests send `source` and `p` (`askPosition`) only when not `index`. Passage cites are labelled by `passageLabel` (`askCiteLabel`: the chapter map's chapter and number through `chapterLabel`, the cite's `number` for an earlier book, else the self-named head of the title; an earlier book's prefixed with `bookShort`; one of this book not wholly before the frontier only "The book") and are links only when `passageOpenable` (this book, `seq` and `end` before `askFrontierSeq()`, checked at click and on every repaint, a focused link that stops qualifying turning plain with focus kept); a link opens `openPassage`, a `sheet()` of `passageBlocks` (the cited blocks also before the frontier, through `h()`), closed on any repaint where the cite stops qualifying, with "Read from here", which closes the sheet at once (`close(true)`; `dom.js` `sheet().close` now really closes on a forced close during a slide-out, `closeLocked`), then `moveTo(blockStart(seq))` through `okToMove` and opens Read, clearing the thread as any move back does.

`ask.answer` makes one call plus at most one retry per question: a found answer with no valid cite at all (an invented cite among valid ones is dropped silently), an outside name, or "the notes" / "the reader" in the voice. The outside-knowledge check runs on every returned answer, retry included: a capitalised token of two or more letters must be in `vocab`, the words of the slice sent (the question's and history's words are not in it), except fixed exemptions (`CAPITALISED_OK`) and, as a sentence's first word, an ordinary word (`SENTENCE_FIRST` = `COMMON` minus `NAME_LIKE`). Unknown question words are banned from the answer and masked in history (lowercase one- and two-letter words are not checked). A capitalised one is an unknown *name* only when not sentence-first or after a title; with no entry named and none carried over (`sl.nobody`) the question is refused without a call (`NOT_SAID`), otherwise the model is called, the name is banned and a closing sentence appended. Known gaps: a remembered fact told only with names the reader has met is not caught, and a name-like common word opening a sentence is refused even when innocent. Earlier answers are never replayed, only earlier questions (unknown words blanked; turns noted `unknown name` or `refused: outside knowledge` are dropped by `historyFor` in `ask.js`) and what they were about, checked against the current view. The model is `pick_model(tier)`; a question holds one of 2 slots while it runs (429 `busy`), and `model.timeout` is 120 s where the backend has one (not Claude). Nothing is stored or logged. The Ask tab is hidden only when there is no model (it stays while Ollama is busy); one line names the model answering now, not kept per answer. The thread lives in memory and is cleared with the field (typed, prefilled or restored text) when the position moves back at all (by anchor ordinal, or by `p` in the same book: two positions inside one anchor's span differ in which blocks are before them), a Finished box is unticked, an earlier book, another order or index is opened, or an edit or merge removes or renames something visible (`revealsLess`: a snapshot of ids, names, profiles, details, ties, events and chapter recaps; not the story recap, which is replaced as the reader goes on). Reading on, into the next book too, keeps it. No spec, schema or protocol change.
8f. **Art sets** (`art.py`, CLI `lorekeeper illustrate`, docs `pictures.html`; in the web app the store, the stage and the routes are `web/art.py`, `web/jobs.py`, `web/app.py`): generated pictures, never part of the index document (the schema is closed, nothing in SPEC changes, they stay out of share bundles and registries). An art set is one folder per edition and style behind a `Sink` (`manifest`, `save`, `put`, `read`; `FileSink` is the CLI's folder `art/<textHash>/<style>/`, and any other store implements the same four calls): `art.json` (`{"lorekeeperArt": "0.1", textHash, style, world, pictures, screened, looks, lookSentences, skipped, cost}`, rewritten after every picture; an older set's `appearance`, `groups`, `intro` and `worldOld` are kept untouched and never read, and at load an unedited `world`/`worldOwn` is moved to `worldOld`, while old final skips "skipped: no look described" are dropped so those portraits are tried again; a set is one style by `style_slug`, so another text with the same slug reuses it and keeps the stored text, and a folder holding another edition's or another slug's set is refused, never overwritten) and files `<id>.<ext>` with `p<8 hex>` ids named from the bytes. A picture record has kind `plate|event|comic|portrait|place|thing`, `target` (chapter title, event id or entity id), `chapter`, `from` (the anchor it shows from, compared by ordinal like every `from`), `sources` (the anchors of this book it was written from, always at or before `from`), `references`, the prompt exactly as sent, provider, model and quality (the image model of its kind and the level it was actually drawn at), `writer` (`{provider, model}` of the text model that wrote the prompt, from `model_ref`; absent for a nameless model and on older records; a same-prompt redraw keeps it, `Prompt.written_by`), shape, cost, `created` and `notes` (`NOTE_VERSION` = 3, the material version it was written from; 2 and absent mean the older quoted appearance notes, and such a picture is never a reference for a new one; older records may also carry `appearance`, never written now). The model only proposes: `Illustrator` (the run; `job`, `make_prompt` and `draw` draw one picture at a time, `job` raising `NotVisible` for a target after a given anchor, `ValueError("no such chapter")` / `"no such event"` for an unknown one, and finding an entity that only an earlier book has in that book, whose set is then saved even when that book is only read; `n` the plan number (a table-of-contents position, so not 1..N: Dracula's Chapter I is 4), `events` its non-minor events, `pictures` what it would get at that level whether chosen or not (at `main` 1 with a main moment or a recap, at `all` its plate plus its other screened moments, so a chapter with a recap still gets its plate when screening finds no moment, or `max(1, non-minor events)` unscreened, at `none` 0), `drawn` how many of those the set holds (non-partial, same kind, target and anchor; unscreened at `all`, the plate only on its own key plus at most `pictures - 1` event pictures, so an on-demand event picture never stands in for a plate), `chosen` whether this run draws its scenes; `plates` sums `pictures` over chosen chapters, `portraits` is the plan's and `new_portraits` the portrait jobs neither held nor finally skipped (`_have`, `_is_new`), and `portraits_max` what `new_portraits` would be if every counted entity without a fresh look index (`_classified`; one with no items counts as checked) got `MAX_VERSIONS`: such an entity adds `max(still to draw, MAX_VERSIONS - portraits of it held or finally skipped)`, a checked one its planned portraits still to draw, so it equals `new_portraits` once every counted entity is checked) decides what is drawn, anchors, references, the cap and every drop. Anchors are placed by fingerprint against the EPUB (`anchors.resolve` and `effective_locations`, the `seq` hint is optional; an unresolved one takes the next one's block, a trailing unresolved one is never reached), and an EPUB none of whose anchors resolve stops the run. Anchor ids repeat across the books of a series (`tocNN.paraMM`), so every anchor in a manifest is one of that manifest's book, except the background note's, which carries its `book` (series book key); an anchor is only ever compared with anchors of its own book, and an earlier book's content counts as read. Several indexes are drawn together only as books of one series; the CLI also refuses an `--epub` that is not the index's `builtFrom` edition and a `--quality` the image model lacks, before any call. **What is drawn:** `main` level is one picture per chapter that has events (its plate: the drawable turning point, else the drawable event whose words the chapter recap shares most, else the recap alone), `all` adds every other drawable moment as an `event` picture, minor events never, and `none` (`LEVELS` = `main`, `all`, `none`; `scene_level` reads `"none"` and `None` alike and refuses anything else before any call) draws no plates or event pictures and never screens, so with portraits it is a portraits-only run; `Illustrator(scene_chapters=...)` is the web's chapter choice, a set of plan numbers `n` (None every chapter, empty none) that limits scenes only and never portraits, while the CLI's `chapters=` (`chapter_filter`, `--chapters`) still also cuts portraits to anchors up to the last chosen chapter (the two combine in `_chosen`), and only chosen chapters are screened; `Illustrator(portraits=<collection of entity ids>)` draws only those people and creatures with a profile in the book, without the main-cast rule (`self.portraits` is then `"chosen"`; empty means none), `until=(book index, anchor id or ordinal)` (-1 the last book; checked at construction, `ValueError("until: ...")`) is a limit no job passes (`_limit`, `_within`; later books never planned, a chapter whose plate is past it never screened, `_reaches`), `_versions` then plans an entity from its items up to the limit only (the first portrait at the first look item in reach, else the first profile in reach, when the book profiles it anywhere; changes after the limit wait), while the look index and look sentences are still made over the whole book, since they only choose, and `finished=` is the run's reader (an unfinished earlier book is never drawn, every job's prompt carries the reader's `finished`, so it is `partial` as the sheet's draws are, and "already drawn" asks `_usable(..., reader, rec)`); `Illustrator.screened` reads a fresh entry), where `key` hashes the chapter's event ids, anchors and summaries so a rebuilt index screens again; portraits (`portraits`, in `Illustrator(portraits=...)` and job config `art.portraits`: `"main"`, the default, `"all"` or off; `True` from an old config means `"all"`) for the main cast, people and creatures with a profile named by at least `max(MAIN_CAST_MIN, ceil(MAIN_CAST_SHARE × non-minor events))` = max(3, 5%) of this book's non-minor events, at most `MAIN_CAST_MAX` = 12 per book ranked by that count, then turning points, then first appearance (a returning character is judged on this book's events only, so a look change in a book where it is minor is not drawn), or under `"all"` for every one with a profile that has a portrait-stage profile or is named by two non-minor events (an on-demand `job("portrait", ...)` is never filtered by either), planned from the *look index* (`items`, `look_index`, `classify`, prompt `LOOK_INDEX`): an entity's items in a book are its facets and profiles (never an arc) and the turning points naming it (`event:<id>`), in reading order, and one cheap call per batch of up to `LOOK_BATCH_ITEMS` = 40 items (small entities share one, a large one takes several) flags each as a `look` (how it looks: body, face, colouring, dress, marks, gear; for a group its members' look) and/or a lasting `change` of its own look (a kept wound, a lost eye, a body remade, a disguise, a new way of dressing; acting on something else, "drags a dead deer", is none, and a death alone is none), a flag kept only for an item number that exists in that call, a turning point counting only as a change; cached as `looks[eid] = {key, items: {id: {look, change}}}`, keyed by a hash of the items' ids and texts, so a rebuilt index is classified again and a resume makes no call; the classifier's change phrase is never stored (the manifest is served whole to the Reader) and nothing it writes reaches a prompt, while every use is filtered by anchor (an item counts only at or after its own `from`); `_versions` puts the first portrait at the first look item, else the first profile, then one per change flag (`Job.change` is the item's own text), up to `MAX_VERSIONS` per book and `MIN_GAP` blocks apart, the old one kept; `counts` plans from cached flags only (an unclassified entity gets one portrait); versions are compared on the anchors they show from, and two that land on one anchor become one, the later; an entity with a drawn portrait in an earlier book is not drawn again without such a change (a later book is planned only once the earlier ones are drawn, so a portrait planned there and then skipped does not count); an entity no item describes still gets its portrait, written from who it is. The look index and the screening are for planning runs only: the prompt path never screens, and makes a look-index call only for an on-demand entity job with no fresh look index (the anchor rule under **Anchors**), beside the look sentences' miss below. **Prompts** (KOAssistant's shape on gated material): one writer call per picture (`make_prompt`, system text `WRITER`, the task line `TASKS[kind]`), the model of its responsibility (below, **Models per job**), on tagged blocks built only from `gating.view` at the anchor and paragraphs at or before it. with a picked set (`look_sentences`) only the picked sentences count, chosen greedily by the words they add (`EARLIER_NEW_PICKED` = 2), without one the look-index-flagged items go first and then earlier profiles, one sentence at a time and only when it adds `EARLIER_NEW` = 2 words; The edit is then **verified** before it is filed: `verify_fix(model, before, after, faults, note="")` (`VERIFY_FIX`, `VERIFY_FIX_PROMPT`, `VERIFY_FIX_SCHEMA` = `{"results": [{"n", "fixed": "yes"|"partly"|"no"}], "changed", "new": [fault]}`; picture 1 the original, picture 2 the fix) returns `Verdict(results, changed, new, checked, cost, why)` with one result per fault in order, numbered from 1 (a skipped fault, an unknown value or an out-of-range `n` counts as "no"), `new` the gross faults the fix added (cleaned, at most `MAX_NEW_FAULTS` = 3), and `counts()` the stored `{fixed, partly, of, results, new}`; byte-identical bytes are a code verdict with no call (all "no", `changed` False, cost 0), even with `verify=False`; a failed call, a blind model or a reply with no boolean `changed` or no `results` list is `checked=False`, no verdict. The verifier is `checker`, else the run's picker. Clients must never derive positions from percentages or page numbers (SPEC §3.7). A fat client (local gating in Lua) is future work (SPEC §11).

Key format ideas that span several files:
- Every gated item has a `from` anchor; comparisons use the anchor's **ordinal** (position in the `anchors` array), never ids or `seq`.
- `replaces` only points backwards (same book earlier, or an earlier series book), so indexes can be generated forward without editing earlier files. Replaced items become `history`, not deleted.
- Entity ids are series-scoped; each book's index lists only that book's names and facets, and `view()` merges across finished books. `carried` is a denormalized fallback used only when the origin book's index is absent.

## Conventions

- Content rules (SPEC §6) apply when editing example indexes: text-only claims with `evidence`, written as the reader understands things *at* the `from` anchor (no hindsight), at most 8 consecutive words quoted from the book. The validator checks the last rule with `--epub`.
- Example anchors use ids like `ch2.para14` (chapter, paragraph within chapter) with `seq` hints for the Gutenberg edition. Author new anchors by `seq`, then run `fill-anchors`.
- Conformance expected outputs are generated by the reference implementation. When regenerating, review the diff, and keep spoiler properties asserted independently in `tests/test_gating.py`.
- Never restart `lorekeeper web` or kill a generate process while a run is active: check `/api/jobs` and **abort** if anything is running, queued or stopping. CLI and Studio runs share one Ollama.
- Commits and releases: pull requests are squash-merged and the PR title is the commit message, in Conventional Commits form (`feat:`, `fix:`, `docs:`...). Never add `Co-authored-by`, "Generated with" or any other attribution trailer to commits, PR bodies or templates. release-please keeps a release PR open on `main` (version in `pyproject.toml`, `CHANGELOG.md`); merging it tags `vX.Y.Z`, which publishes `ghcr.io/nightspine/lorekeeper` (`latest`, `X.Y.Z`, `X.Y`, `edge` for main, `sha-` tags). See RELEASING.md.
- Schemas in `schema/` are normative and versioned with the spec (`"lorekeeper": "0.1"`). Keep the schemas, SPEC.md and the code in agreement in the same change.

## Working as lead
