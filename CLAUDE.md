# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Lorekeeper is a draft open standard (SPEC.md) for spoiler-gated book indexes ("X-Ray"-style companions), plus a Python reference implementation. The spec is the product; the Python code exists to make the spec testable and to serve later as the basis for a self-hosted server and generator. Reader apps (KOReader, iOS readers) are meant to consume indexes without any AI.

## Commands

```sh
uv sync                                   # install (Python ≥3.11, deps: jsonschema; dev: pytest)
uv run pytest                             # all tests
uv run pytest tests/test_gating.py::test_cross_book_replacement   # one test
uv run lorekeeper conformance             # run conformance cases
uv run lorekeeper conformance --update    # regenerate expected views after an intended gating change
uv run lorekeeper validate examples/sherlock-holmes/study-in-scarlet.json examples/sherlock-holmes/sign-of-four.json --series examples/sherlock-holmes/series.json
uv run lorekeeper validate examples/sherlock-holmes/study-in-scarlet.json --epub corpus/pg244/pg244.epub   # + anchor & quote checks
uv run lorekeeper blocks corpus/pg244/pg244.epub --start 100 --end 150    # list blocks (seq, spine, words, fp, text) for authoring
uv run lorekeeper fill-anchors INDEX --epub EPUB --write                  # compute fp from seq hints, record edition hashes
uv run lorekeeper toc corpus/pg244/pg244.epub                             # chapter numbers for --chapters
uv run lorekeeper generate corpus/pg244/pg244.epub -o out.lore.json --chapters 5-6   # needs Ollama running
uv run lorekeeper generate ... --resume                                   # continue an interrupted run
uv run lorekeeper generate ... --provider gemini --model gemini-2.5-flash # bring your own key: claude|openai|gemini|openrouter|mistral|groq|xai|deepseek|custom (key from the env var, or --api-key-file PATH; --base-url for custom)
uv run lorekeeper profiles INDEX... --tidy                                # older indexes: drop description-entities, backfill profiles (Claude; backups first)
uv run --extra claude lorekeeper portraits INDEX...                        # rewrite profiles from every passage mentioning each entity (Haiku; --prior earlier books; backups first)
uv run lorekeeper illustrate INDEX... --epub EPUB... --style ink --level main --provider gemini --quality draft --cap 3   # chapter pictures and portraits into art/<textHash>/<style>/ beside the index (resumable; --limit N, --chapters 4-6, --prior INDEX for earlier series books)
uv run python bench/model_bakeoff.py MODEL...                             # compare Ollama models on one passage
uv run --extra claude lorekeeper arcs INDEX...                             # write a short per-book arc for each main character from the index's events (cheap model; --prior earlier books, --redo; backups first)
uv run --extra claude python bench/ask_eval.py INDEX... --series S --book B --at 0.33 --provider claude --model claude-haiku-5-5 [--fresh] [--roster N] QUESTION...   # try Ask on an index at a position; prints slice size, picks, answer, cost
uv run --extra web --extra claude lorekeeper web                          # Library, Reader, Runs UI on :8765
uv run lorekeeper web --no-auth                                        # skip the web app sign-in (trusted local use only; or env LOREKEEPER_AUTH=off)
uv run lorekeeper reset-password [--data DIR]                             # new generated admin password, printed once; forces a change and ends all sessions
uv run lorekeeper web --api-token TOKEN                                # require a bearer token on /v0 (or --api-token-file PATH, or env LOREKEEPER_API_TOKEN)
uv run lorekeeper docs export build/                                      # landing page (site/) + docs + spec + styles, for hosting
uv run lorekeeper share INDEX --epub EPUB -o bundle.json                  # a share bundle: scrubbed index + builder attestations (--series for a series book)
uv run lorekeeper registry add bundle.json --publisher NAME --source DIR  # check and file a bundle in a registry tree (check: same, writes nothing; remove ID --reason TEXT)
uv run lorekeeper registry build DIR -o build/registry --base-path /lorekeeper-registry   # the static registry: lookup files per edition, listings, indexes
docker compose up -d                                       # same server in a container on :8765, data in the lorekeeper-data volume (env: LOREKEEPER_DATA/HOST/PORT/OLLAMA_URL/API_TOKEN)
node tests/js/run_conformance.mjs                                         # JS gating vs conformance cases
uv run python bench/compare_handwritten.py out.lore.json                  # generated vs hand-written example
```

The generator needs a local Ollama (`brew services start ollama`), or a cloud provider with your own key (every provider in `llm.PROVIDERS`: `llm.OpenAICompatible` serves all but Claude, which uses the anthropic SDK). Default model is `gemma4:12b-it-qat`; `qwen3.5:9b-q4_K_M` is the faster alternative. Thinking mode is deliberately off. A two-chapter run takes tens of minutes on a 16 GB M4, so run it in the background. Tests use a scripted fake model (`tests/test_generate.py`) and never call Ollama.

`corpus/` is gitignored; the README lists the download commands (pg244, pg2097, pg345 and the Standard Ebooks Scarlet). `examples/dracula/dracula.json` is a complete generated index of pg345 that the Library, the Docker image and the landing-page demo ship with; it must pass `lorekeeper validate --epub corpus/pg345/pg345.epub`, and `bench/site_demo_data.py` flattens it for the site. Tests that need a corpus EPUB skip when it is missing, so a green run without the corpus doesn't cover anchor resolution or quote checks.

## Architecture

The pipeline, in spec order:

1. **Text model** (`epub.py`, SPEC §3.1): EPUB spine → paragraph-level blocks → `seq` numbers. Standard library only (zipfile, ElementTree, html.parser). A document with no `p`-style blocks but real text (Calibre's `<div class="p">` paragraphs) is re-parsed with `div`/`blockquote`/`section`/`article`/`aside` as blocks (`FALLBACK_BLOCK_TAGS`, §3.1 rule 6); it only ever applies per document, so books that already parse keep their seqs and text hashes.
2. **Normalization and fingerprints** (`text.py`, §3.2–3.4): `words()` and `fingerprint()` are the cross-language contract. Every port (Lua, Swift, Kotlin) must produce identical output. Any change here changes every anchor in every index: run `fill-anchors` on the examples and update SPEC §3.2.
3. **Anchor resolution** (`anchors.py`, §3.6–3.7): the client side. It maps a reader's own edition onto an index's ordered anchors. Unresolved anchors take the *next* resolved anchor's location, so mismatched editions can only under-reveal. Keep that invariant.
3b. **Locators** (`locators.py`, §3.7): `locate(book, locator)` turns what a reader app holds (`{"block"}`, `{"cfi"}`, `{"xpointer"}`, `{"spine","word"}`, `{"spine","progress"}`) into the seq of the block it points into, rounding to the *preceding* block when in doubt (-1 before the first block; `exact=False` when a fallback decided), and `position(..., inclusive=)` gives the current anchor in the two modes: "finished" (the current block does not count, for views) and inclusive ("who is this on my page?"). `web/position.py` (Book Orbit) is built on it. Cross-language vectors live in `conformance/locators/` (run by `lorekeeper conformance`; skipped when the corpus EPUB is missing).
4. **Gating** (`gating.py`, §7): `view(indexes, Position, series, order, finished)` is the normative algorithm. Its output shape is `schema/view.schema.json` and is what `conformance/*.json` freezes.
5. **Generation** (`generate.py`, `llm.py`): `llm.PROVIDERS` is the one table of cloud providers (label, kind `anthropic`/`openai`, base URL, key env var, key URL, preset models with prices and a `cheap`/`strong` tier); it is the only place to update text model ids and prices (image models and their per-picture prices are in `llm.IMAGE_PROVIDERS`, below), and a stale preset never blocks anything because the UI also lists live models from `GET {base_url}/models`. `llm.make(provider, model, api_key, base_url)` dispatches on it. Pictures have a second table, `llm.IMAGE_PROVIDERS` (Gemini and OpenAI only, the only place for image model ids and prices, which are per quality level and where published per shape, `None` = "price unknown"; label and key variable come from `PROVIDERS` via `image_spec`; `image_price`, and `make_image` which dispatches on it and raises `ValueError("Claude cannot draw")` for Claude), whose backends live in `images.py`: one `draw(prompt, shape=, quality=, references=)` returning `Drawn` (bytes as the provider sent them, mime, cost), at most 6 reference pictures sent before the prompt, a safety refusal as `ImageRefused` with the provider's wording; `lorekeeper draw` tries a prompt. `OpenAICompatible` is stdlib-only: json_schema first, plain json_object with the schema in the prompt after a 400, and it adapts to models that reject `max_tokens` or `temperature` on the first 400; unpriced models cost 0 in `Usage` and show "price unknown" in the UI, never a made-up number. It reads chapters (from the EPUB table of contents, `epub.read`) in chunks of whole blocks. Per chunk: one extraction call, a rephrase call if a claim copies 9+ words of the book, one support-check call. Facets describe what an entity *is* (role, look, nature, allegiances, status); plot goes to events. The extraction also returns **profiles**, for every new person, creature and group and for anything it learns something lasting about (a new entity's one-sentence `desc` reads like the first line of a character sheet and, when the response has no profile for that entity, is committed as its first profile instead of a plain fact; with a profile it is dropped as a duplicate): a self-contained "who this is now" for entities whose picture changed, committed as `kind: "profile"` facets that replace the entity's current profile, including one inherited from an earlier series book, so a character keeps one growing description (the Reader shows the latest visible one). Those extraction profiles are pieced together one passage at a time; `portraits.py` rewrites them afterwards the way a reader would: at each chapter end, for every entity mentioned at least 2 times (rewritten once at 4 mentions if the first came from fewer, then again once mentions grow by half, and at the next chapter end after a checked fact records a change in standing, `portraits.STATUS`: died, married, captured, revealed...; a thin tie or role is stated plainly), it sends the paragraphs around every mention so far (up to 40, sampled evenly, first and last kept; a name counts only if no other entity shares it, so "Harry" but not "Potter") together with the entity's last 8 checked facts, and asks for a character-sheet description, not a plot summary, whose first sentence states any lasting change in standing the passages show ("Dead, killed by..."); a change in standing recorded since the last portrait, as a checked fact or as a turning point naming the entity ("Lucy dies"; `changes_standing`, which ignores hedged phrases such as "near death" or "fears she is dead", `HEDGED`), is quoted in the prompt, the portrait is never revealed before it, and one whose first sentence does not state it (a death needs a death word, `DEATH`; "engaged" does not count) gets one rewrite ("rewritten: change in standing"); a rewrite may not drop a death the previous portrait opened with: one retry, else the previous portrait stands ("dropped: lost the change in standing"). Only text up to that point is sent and the portrait is revealed at the first anchor after the last paragraph used. A portrait naming a word the book hasn't used yet (model memory) is dropped; "now"-style wording gets one rewrite. A profile, desc or portrait that states a tie (wife, fiancée, mother, heir: `generate.TIE_WORDS`) the passage or the entity's notes never use is dropped ("dropped: tie not in the text"; portraits get one rewrite first, and for them the sampled passages, the entity's checked notes and profiles up to that point and the previous portrait all count as support), because models upgrade "someone Harker keeps notes for" to "Harker's fiancée" from memory. Portraits replace extraction profiles from their first one's reveal point on (one at that same anchor goes too); earlier ones stay as the early description, and a rewrite that lands on the previous portrait's anchor stands in for it rather than sitting beside it. Every finished web run writes them as a "Writing descriptions" stage (`JobManager._portraits`: the cheap model of the run's own cloud provider, else of the first configured one, about 20 cents a novel on Haiku, skipped without any cloud key; a failure there keeps the index as the run wrote it). `arcs.py` then writes each person, creature and group a short **arc** per book, `kind: "arc"` facets (1 to 3 sentences, at most 400 characters, about this book only; SPEC §4.2, limit §6.3, view rule §7.3.5), from the index's checked events and not the book text: at each chapter end an entity gets one when it is named by 2 non-minor events or a turning point and has none yet, then again after a turning point or 2 more non-minor events name it; the prompt holds its latest profile as context, its events up to that point, its ties and its previous arc, the portrait checks run with a 400 limit (unknown names, hindsight wording, unsupported ties) plus a sentence count, `ABOUT_THE_TEXT`, no chapter references (`CHAPTER_REF`) and, with the EPUB, the 8-word copy rule, with one rewrite then a drop, `from` is the anchor of the latest event the writer was given (never before the entity, a name it uses or the arc it replaces; SPEC §4.2 only requires it at or after the latest event the arc tells), the reply names which events it tells (`told`; a reply without a valid list gets the one rewrite, then every event sent counts as told), `evidence` is exactly the union of the told events' evidence and `replaces` the same book's previous arc. It runs as the stage after "Writing descriptions" and the reapplied edits (`JobManager._arcs`, same cheap model, skipped for a local run and without a cloud key, a failure keeps the index), and `lorekeeper arcs` backfills older indexes. A kin or role word is never a person: a proposed person or added name that is only such a word once a leading article, possessive pronoun or plain adjective is taken off (`bare_kin_word`, `BARE_WORDS`: "Father", "Mama", "the boy", "my mother") is dropped ("dropped: kin or role word, not a name"), while a kin word with a proper name ("Uncle Vernon", "Father Brown", "Mother Superior") or with the name in a note ("Mama (Auriél)") is a real name ("Big Brother", "The Stranger" and "Porter" are names too: only kin words and boy/girl/man/woman/lad/lass/child/baby are bare; the loss of books whose protagonists are only "the man" or "Ma" is accepted, since vague kin words becoming people was the complaint), as is a name in a note after a bare outer ("the boy (Harry)"). A possessive kin description ("Gabriel's sister", `kin_description`) resolves to the one named entity the companion already ties to Gabriel that way, from this book's ties or an earlier book's (`kin_ties`: "sister of" either way round, a sexed word excluding the other sex, modifiers agreeing: an unmodified "father" never matches "stepfather of", "elder sister" never "younger sister of"; stat "kin descriptions matched to a known relative"), is dropped when several fit ("dropped: kin description fits several") or when its owner is not a known named entity ("dropped: unnamed relative of no one known"), and otherwise, like any description ("the old priest"), becomes an entity only if the same reply gives it a part in an update, tie or event ("dropped: unnamed relative with no part"). When a tie makes exactly one named person that kin of X and exactly one such description exists, the named entity is folded into the description at the end of the part, so the description's id stays and no id names someone the reader has not reached (`_fold_kin_descriptions`, "merged: kin description into the named relative"), but only if the person is this book's own, the identifying tie was revealed at or before their first appearance (a tie stated chapters later would give a twist away), the description's notes do not keep the identity back and no turning point names both (`hidden_identity`); `profiles --tidy` does the same to older indexes and removes person entries named only by kin or role words. Names must appear in the passage (a name the model knows from elsewhere is dropped: it could name someone before the text does); a new entity is introduced at the first verbatim use of its name in the indexed text (`earliest_mention`), never later than needed; people named together ("Mr. and Mrs. X") are split into two (`split_couple`); matching (`match_known`) respects titles (Mr/Mrs never match), plural and reordered forms, a full name for someone known only by title and surname, a tail form ("Van Helsing" / "Abraham Van Helsing") and middle names or initials (`merge.same_person_name`). A proposed name goes through `resolve_name`: when it fits two or more known people (`ambiguous`), it never creates a third entity; if the hits all match each other by name and nothing forbids it (`_may_merge`: no `Options.distinct` pair, no relation between them, no title of another sex, no two different full proper names) they are folded into one in-run (`_merge_entities`, logged in `added` as kind "merge", stat "merged by a bridging name"); otherwise a small `DISAMBIGUATE` call over the three paragraphs around the name picks one, "both" or "none" (at most `MAX_DISAMBIGUATE` per chunk), as it does for a new bare first name while a person known only by title and surname is in the passage. The model's `names` list is not trusted: each entry is a (name) claim in the fact-check, a name already carried by another entity is never added to a second one, and a bare family surname is never a name, and a person never takes a name the text gives a relative (`names_a_relative`: "her mother Mrs. Westenra", "daughter of Mrs. Westenra" in the cited paragraphs or the entity's notes) or, for a titled name, one any sentence read so far uses beside the entity's own name as a second person (`names_two_people`: "Mrs. Westenra was anxious concerning Lucy"), stat "dropped: name of a relative". `earliest_mention` searches a titled name only in its exact form ("Mrs. Harker" must not inherit chapter one from "Jonathan Harker"). The fact-check (`VERIFY`, optionally a stronger `Options.check_llm`) gives every claim a verdict with a one-line reason: `unsupported` drops it (kept with its reason under `rejected` in the `.report`), `unsure` keeps it but lists it under `unsure` (stat "kept: checker unsure"), and a claim with no verdict is accepted; it sees earlier chapter recaps for recap claims and moves facts that narrate a moment into events, except descriptions (`DESCRIPTIVE`, "A tall man in black who..."), which stay facts. Events are every development that changes the situation, up to `max(6, words/200)` per chunk, each weighed by the model as `turn` (a turning point: revelation, twist, reversal, realization, death, a decision with no way back), `plot` (an ordinary development, stored as no `kind`) or `minor` (a small moment; `EVENT_KINDS`, SPEC §4.4), and the prompt names the chapter the passage is from. Each event may carry a `setting` (where it happens, as the book states it, fact-checked like a claim and linked to a known place entity); the Timeline groups a chapter's events into scene runs headed by the setting and the position panel shows the last known setting in the current chapter. The chapter summary asks for complete sentences on what the passage does to the story, leaving out scenery, meals and travel details; a summary sentence or event under `MIN_SENTENCE_WORDS` words (a heading or a label such as "unresolved") is dropped ("dropped: not a sentence"); a chunk whose summary comes back empty gets a chapter recap made of its own checked events, minor ones left out ("chapter recap from events"). The context block lists each mentioned entity's existing ties (`_ties`), and the prompt asks for a relation only when the companion lacks it or the passage changes it. A relation is a lasting tie, never one action, with a `kind` (`RELATION_KINDS`: family, romance, friendship, alliance, service, hostility, acquaintance, place; SPEC §4.3): a label over `MAX_TIE_WORDS` is dropped ("dropped: not a tie"), a passage keeps one tie per pair and kind, the one shown latest ("dropped: second tie for a pair"), the fact-check lists ties that narrate one action under `moments` and they are dropped ("dropped: an action, not a tie"), and a new tie of the same kind between the same two `replaces` the current one (`_current_tie`, "ties replaced by a newer one"), so "fiancée of" becomes history when "wife of" arrives. The story recap walks the whole arc so far and then the recent stretch (up to 10 sentences); a recap or summary that talks about "this passage" is dropped (`ABOUT_THE_TEXT`) and the previous one stays. Chunk size defaults to `default_chunk_words(provider)`: 8,000 words (about a chapter) for a cloud provider, 2,500 for Ollama; the build form and the CLI follow the provider unless a size was chosen. `Options.chunk_mode` `"chapter"` (CLI `--parts words|chapter`, default per provider, `--whole-chapters` kept as an alias for `--parts chapter`; job config `chunk_mode`, the build form's "Read whole chapters"; on by default for a cloud provider and off for Ollama in the form and the CLI (`default_chunk_mode`), while a job config with no `chunk_mode` means words; an explicit `--chunk-words` alone means words, `--resume` keeps the mode recorded in `.state`; the form follows the provider unless the person chose) makes a part a whole chapter whatever its length, so there is one call and one chapter recap per chapter and the prompt calls the passage "the whole of <chapter>". A chapter over `max_part_words` (`MAX_PART_WORDS` = 20,000 words for a cloud provider; `max(1500, (num_ctx - 4096 - 3000) × 0.7)` words for Ollama, never above the cloud cap) is cut at a scene break in the last 40% of the words so far (`is_scene_break`: a short heading-like block only; `epub.py` drops wordless blocks, so `* * *` rows never reach it), else at the paragraph where the cap is reached. If a reply is cut off (every provider) the part is split in two and each half is read again. Each part after the first, the first part of a chapter included, gets a "Where the previous part left off:" bridge (the last two blocks, at most 150 words) as context only: no claim may cite it and the fact-check is told so. The Claude backend sends no sampling parameters (the API rejects `temperature` since 2026-10-21); Ollama and OpenAI-compatible backends use 0. Proposed names pass `triage_name` first: possessive descriptions of things ("Gabriel's fear") are dropped, descriptions wrapped around a name ("Celene's brother Gabriel", "Chevalier of the Golden Host (Gabriel)") resolve to that entity; unnamed people ("Gabriel's daughter") stay. The extraction also returns a story-so-far recap and a list of summary sentences; each sentence is fact-checked on its own and the survivors become a `scope: "chapter"` recap (one per chunk, titled with the chapter, so a long chapter has several parts the Reader joins). The model only proposes content. Python assigns anchors, ids and reveal points: `from` = the last cited block, then snapped *forward* to the next anchor-eligible block (≥ 6 words, unique fingerprint). Python also matches names (`match_known`, `mentioned`: exact, without honorifics, or a unique surname) and drops anything that fails a check. The index and a `.state` sidecar are written after every chunk, which is how `--resume` works. A `.report` sidecar holds drop counts by reason.
6. **Web UI** (`web/`, optional `web` extra): FastAPI app (`app.py`) plus `jobs.py`: a content-addressed book store and a single-worker job queue (one Ollama model at a time) that persists job metadata and an events JSONL under `lorekeeper-data/`. It streams events to the browser over SSE. The frontend is no-build vanilla ES modules in `web/static/`. Store: `lorekeeper-data/auth.json` (0600, atomic write like `secrets.py`): `users.<name>` = `{hash, mustChangePassword, created, changed}` and `sessions.<sha256 hex of token>` = `{user, created, seen}`. 7. **Library catalog** (`web/catalog.py`, `web/bookorbit.py`): the Library browses **books**, and index files are *versions* of a book. A version is matched to a book by its edition text hash, so it needs the book's EPUB on disk. Book Orbit books are a synced cache (`lorekeeper-data/bookorbit/books.json`) holding only books with an EPUB (comics and PDFs have no text to index), plus per-library counts. After signing in the user picks which Book Orbit libraries to show (`bookorbitLibraries` in `library.json`; absent means all, and a new connection clears it); `Catalog.bookorbit_books()` applies both filters. Their EPUB is downloaded on first build (`prepare`) and linked in `library.json`, which also holds each book's default version and manual series for uploads. Series come from Book Orbit, from EPUB metadata (`epub.read`: EPUB 3 `belongs-to-collection`, then Calibre's series meta), or from the user, and are grouped by slugged name. `preflight` reports earlier books with no index and numbering gaps (`notInLibrary`). Builds that go through the catalog get `series_id`/`book_key`, a written series manifest, and `prior` = earlier books' default indexes (`Generator._load_prior` / `_localize`: returning entities keep their ids, cross-book `replaces`, the story-so-far carries over). Front and back matter is decided once, server-side (`web/jobs.py` `NOT_STORY` / `is_story`). A run that covers every story section is marked complete (`Options.whole_story`). Book Orbit auth is username/password with `clientKind: "native"`. Only the rotating refresh token is stored (in secrets), never the password. The access token is in memory and refreshed on 401 or expiry. Lorekeeper never writes to Book Orbit: `BookOrbit._call` refuses every non-GET except the `/books/query` read before any request is made (tested), and the Reader never pushes a position back. In the Reader, a Book Orbit book that isn't finished treats the synced position as a spoiler line: the slider stops there while dragging, and any deliberate move past it (release, percent, chapter jump, next reveal) asks first (`moveTo`); "Show me anyway" allows it for that session and the source line says so, "Back to Book Orbit's position" clears it. `GET /api/library/{key}/position` (read-only) reads the user's Book Orbit reading progress for the book that owns that index (`BookOrbit.progress`: newer servers answer `GET /reading-progress?bookId=`, older ones only `GET /books/{id}/progress`, a flat row per file, normalized to the same shape) and returns `{synced, source, updatedAt, percentage, basis, seq, p}`, or `{synced: false, reason}` (`not-bookorbit`, `not-connected`, `no-edition`, `unreachable`, `no-progress`) so the Reader degrades quietly; `p` is the fraction of words before block `seq`, so the block being read never counts as read. `web/position.py` `resolve` picks the first usable of EPUB CFI (the id asserted on the target element, else the character position inside the XHTML), Kobo (spine file plus percent), KOReader XPointer and the whole-book percentage, using each `epub.Doc`'s `spine_child_index` because CFI and KOReader spine steps count `linear="no"` items too; an exact position more than 5 points away from the percentage is stale (another device moved on) and the percentage wins, and it never raises.
8. **Entity identity** (`merge.py`, `web/identity.py`): one set of name rules (`core`, `extends`: titles stripped, parenthetical notes and possessive descriptions ignored, a shorter prefix form counts for people only) is shared by `Generator.match_known` and duplicate detection. `candidates` groups matching entities across a series: groups where everyone matches everyone are `sure`, others are offered pair by pair. `merge` folds one id into another in every index of the series. It is spoiler-safe because names and facets keep their own `from`, except for hidden identities ("the stranger" is Gabriel), which must never be merged. The web layer only rewrites generated indexes, refuses while a run writes one, snapshots files to `lorekeeper-data/merges/<id>/` for undo, and keeps "not the same" pairs in `library.json` (`distinct`). The Reader suggests a pair only when both entries are visible at the reader's position. Beyond name rules, a model reading short descriptions of the cast proposes pairs the names can't show ("Mr. Dursley" / "Uncle Vernon", `merge.propose`, Haiku). Every pair, proposed or by name, is then judged (`merge.judge`, Sonnet 5.5 when a Claude key exists, else the same model as propose; `judge_model` / `strong_judge_model` in `web/app.py`) from the whole entry of each side (full latest profile, up to 8 details, up to 8 ties as sentences, where it is introduced), the paragraph where the later entry's name first occurs in the book with one paragraph either side (EPUB found by the index's `editions[].textHash`; judged without it when the EPUB is missing), and any paragraph where both names occur as separate mentions. The verdict (`same`, `different`, `unsure`) comes with a one-line `because` that is stored (state `because`, and the merge journal) but never shown to readers, since it may state whole-book facts. A pair left `unsure` without the text is judged once more when the EPUB is on disk. Bump `merge.JUDGE_VERSION` when the prompt changes. Policy (`identity.auto_ok`, `Identity.auto_merge`), all as one undoable step after each check: judged `same` merges automatically when the pair is a same or fuller name, a shared alias where at least one shared name is a proper name (`merge.proper_name`: "Aaron", "Van Helsing", not "the Professor", "the stranger", "Forever King"), or a model-proposed pair whose names are all proper names. Shared descriptors only (the shape of a hidden identity) always go to review. `different` pairs are stored and not listed. `unsure` pairs are listed as "Couldn't tell from the text". In a group where an entry fits several others ("Chloe" fits two Chloes) a pair is merged only if neither entry is in another live suggestion. Family surnames and bare titles are not evidence of identity (`merge.family_names`). Display names (`merge.rank_names`) prefer an entity's actual name over titles: a title word anywhere marks a title ("Forever King"), a shared family surname marks a real name ("Fabién Voss"); the generator applies the same ranking when a new name arrives. Measured on real books on 2026-10-28: the Empire of the Vampire series went from 137 listed pairs to 17 for review, and a fresh Dracula build leaves none.
8b. **Editing by hand** (`web/editor.py`, `web/static/js/editor.js`): the Reader's edit mode (the "Edit" button, `edit=1` in the URL; only for an index built here with its EPUB on disk) lets a person add, change and delete entries, names, details and descriptions, connections, events and recaps, and start an index from nothing ("Write it myself" on the build form, `POST /api/catalog/books/{key}/handmade` → `Editor.blank`: one anchor, no generator, contributor role `author`). Every change is one `POST /api/library/{key}/edits` with an `op` (`add-entity`, `set-type`, `delete-entity`, `add/edit/delete-name`, `-facet`, `-relation`, `-event`, `-recap`, `set-complete`) and one entry in the merge journal (`Identity._commit` with `kind: "edit"` and a `what` line), so `POST /api/library/{key}/undo/{id}` reverts edits and merges alike, and the toast after each change offers it (inside the drawer while the modal drawer is open, since it makes the page inert; an ordinary toast beside the pane). Nobody types an anchor: an op names a paragraph `seq`, and `_Ctx.anchor` snaps forward to the first block with 6+ words and a unique fingerprint, reusing an existing anchor or minting one in the generator's id scheme; `coverage.through` moves forward to it when needed, an entity's `from` is always its earliest name's. `GET /api/editions/{hash}/blocks?seq=&before=&after=` feeds the paragraph picker (`eligible` says whether a block can carry an anchor). Entity-wide ops (`set-type`, `delete-entity`) reach every index of the series; item edits only the book that holds the item. Arcs are read-only (a summary of many events: `add-facet` with kind `arc`, `edit-facet` and `delete-facet` on one answer 400; nothing rewrites an arc after a hand edit, so change the events and the next build writes it again after edits are reapplied, or run `lorekeeper arcs --redo`). Text goes through `check_wording`: the spec's length limits, `generate.HINDSIGHT`, `MOMENTARY` for descriptions only, `unsupported_tie` against the cited paragraph and its neighbours, and the 9-word copy rule (both only with the EPUB on disk); a refusal is a 422 with `code: "wording"` that the form shows under the field. Each edit is also recorded in `lorekeeper-data/edits/<textHash>.json` with its journal id and a target (entity id, item id, original text), undo removes it again, and `JobManager.after_run` (`Editor.reapply`) puts them back on every new build of the same edition: by id when it survived, else by the entity and the original text, skipping what no longer applies ("your edits: 5 applied again, 1 no longer apply" in the run log). An edited index is still a plain SPEC 0.1 document: the only trace in the file is `provenance.updated` and a contributor with role `editor` (`author` for a hand-made one).
8c. **Registries** (`registry.py`, SPEC §8.7, `schema/listing.schema.json`, `schema/share.schema.json`): how an index is shared. Nothing about the index document changes. `lorekeeper share` makes a bundle (the index with every edition's `label` and `fileHash` scrubbed, the series manifest for a series book, optional `derivedFrom`, and builder attestations when the EPUB is given: `book-checks` from `check_against_book` and `spoiler-gate`, which counts names whose `from` anchor comes before the book's first verbatim use of the name). A registry is a tree of files (`indexes/<publisher>/<slug>/listing.json`, immutable `v<N>.lore.json`, `series.json`, plus `removed.json`); `registry check`/`add` treat a bundle as hostile input, since they run in the registry repository's GitHub Action with write access: paths come only from the validated publisher and the computed slug, the 5 MB cap applies before parsing and again to what would be stored, nesting past 32 levels, NaN/Infinity, lone surrogates and non-ASCII or non-UTC timestamps are refused, and every refusal is a finding, never a traceback. Licences are CC0-1.0 or CC-BY-4.0 only. A series is shared as a set under one publisher: a later book `requires` the earlier listings, a new version of an earlier book may not break the later ones, and `remove` refuses a listing others require unless `--with-dependents`. Attestations say who vouches (`registry`, `builder`, `reader`); builder and reader ones are self-reported and a client must show that, never one merged number. `registry build` writes the static profile deterministically (`.well-known/lorekeeper` with `static: true`, `v0/lookup/{text|isbn|gutenberg|openlibrary|wikidata}/<value>.json`, listings, byte-identical index copies); a static host cannot send the digest as `ETag`, so a client MUST verify fetched bytes against the lookup digest. The community registry is `nightspine/lorekeeper-registry` (served by GitHub Pages; its takedown policy is `TAKEDOWN.md` there). The app's side is 8d.
8d. **Community indexes** (`web/community.py`, `audit.py`, `web/static/js/community.js`): the app side of registries, off until the person opts in (`community` in `library.json`: `enabled` null = not asked, asked once on a build page; a lookup tells the registry which book you own). Only the server talks to the registry (default `https://nightspine.github.io/lorekeeper-registry`; https, or http to localhost), and everything it returns is untrusted: one 10 s deadline per fetch (the fetch runs in a thread whose sockets are shut when the deadline passes) that covers connecting, redirects (at most 3, each followed only under the registry's origin and path, like hrefs), headers and body, a 6 MB cap, the guarded parser from `registry.py`, a lookup checked as an envelope and then result by result (at most `MAX_RESULTS` = 200 considered, each stopped at its first schema error), hrefs confined to the registry's own origin and path, the digest verified on every fetched index, impossible attestation counts ignored, and one bad result or listing dropped rather than failing the response. A listing or index is fetched and installed only through an edition whose `textHash` is the reader's and which is the index's only `builtFrom: true` edition (two would let the Reader place anchors against another copy; `builtFrom` exactly true is the one meaning of "exact" in the Reader, `check_against_book` and here; a listing carries no `builtFrom`, so the check is on the index); fetch also refuses (422 `invalid`, nothing cached) an index with an anchor whose `seq` hint is not where its fingerprint resolves, an unresolved one included, since the Reader places anchors by seq on an exact edition (anchors without a `seq` are only reported); any refusal at fetch also removes the cached file and its audit; a fetch past its deadline has its sockets shut (a connection that comes up after it closes itself, `cancel`) and at most `MAX_INFLIGHT` = 4 run at once; a file name too long to store is refused, and `registry_slug` keeps a non-default port. This version offers exact-text matches only (a listing edition's `textHash` equals the EPUB's) and hides series listings. `GET /api/community/books/{catalogKey}` answers a state (`off`, `ask`, `no-edition`, `unreachable`, `ok`) and ranked results (complete first, no early names first, audits with a Wilson lower bound of supported/(supported+unsupported) at or above 0.5, then unaudited, then weak audits, then newer); the lookup is cached 10 minutes and served stale when the registry is down. Fetch stores the verified bytes in `community/cache/` (20 most recent kept) and runs `check_against_book` and `registry.spoiler_gate` against the EPUB; the preview is the Reader on that cached document (`#/preview/<digest>`), held at the end of chapter 3 with the `moveTo` confirm; install copies it to `community/indexes/<registry>--<publisher>--<slug>--v<N>.lore.json` (Library source `community`), read-only (edits and merges answer 409), never pinned as the default on a first install and ranked below anything built here on ties. Two measures are shown, each with who vouches: fit, and checked ("N of M claims held up" from an audit, M = supported + unsupported, with the unsure count as a second sentence, else "Anchors and quoting checked"); the headline says only "Whole book" or "Partial". `audit.audit(index, blocks, llm, n=50)` samples claims that cite a passage (non-profile facets, ties, events, at most a tenth chapter-recap sentences) evenly across the book and asks whether the passage states or clearly implies each (`supported`, `unsupported`, `unsure`); paragraphs are sent whole, a recap sentence gets the stretch its recap covers, `audit.estimate` prices a run from the real prompts, and the app offers an audit only with a cloud provider's strong model (409 `needs-cloud-model` otherwise). Sharing (`share/check`, `share/audit`, `share/bundle`) builds the bundle with `registry.make_bundle`; the dialog never shows book text (counts and item paths only), a stored audit is keyed to a hash of the audited content so a licence change keeps it, and `set-license` is not a hand edit. Submission is the registry repository's GitHub issue form, opened in a new tab.
8e. **Ask** (`ask.py`, `common_words.py`, `web/app.py` `GET /api/ask` and `POST /api/library/{key}/ask`, `web/static/js/ask.js`, docs `ask.html`): questions about the book answered from the index, never from book text. The route builds `gating.view` at the reader's anchor (with `finished` and `order`; the body may carry `book`, a mismatch with the index's series book is 422 `bad-position`), and `ask.select` picks what the model sees as plain text notes under a character budget (`DEFAULT_BUDGET`, a smaller `OLLAMA_BUDGET`): a header (book titles only when the view spans more than one book), the entries the question names (`merge` name rules, kin words followed through connections for follow-ups), their profiles, details, connections (capped per entry) and events oldest first, with the first and the last few put first in line, then chapter recaps found by word match (capped at a quarter of the budget). Chapter questions (`chapter_matches`: number or numeral, last/latest/this/current of the named book else the current one, previous, a written-out title) take the asked-for parts outside that cap, up to half the budget, shortened as needed; a book with no recaps gets a note, never another book's. With a cloud model (`roster_chars` = `ROSTER_CHARS`; 0 for Ollama) a question that names nobody first makes one pick call over `ask.roster`, and a who/whom/whose/which/where/called/name question about a named or carried entry with other content words makes one over `neighbours()` when it has any (ties and shared events). Ollama gets neither list, but still a names-only `_pick` when nobody is named and no words match. Measured on Haiku, on one 700-entry series: about 9,000 to 19,000 tokens and 0.1 to 0.2 cents for a question that names someone, about 0.6 cents with the roster pick; a small index sends far less.

`ask.answer` makes one call plus at most one retry per question: a found answer with no valid cite at all (an invented cite among valid ones is dropped silently), an outside name, or "the notes" / "the reader" in the voice. The outside-knowledge check runs on every returned answer, retry included: a capitalised token of two or more letters must be in `vocab`, the words of the slice sent (the question's and history's words are not in it), except fixed exemptions (`CAPITALISED_OK`) and, as a sentence's first word, an ordinary word (`SENTENCE_FIRST` = `COMMON` minus `NAME_LIKE`). Unknown question words are banned from the answer and masked in history (lowercase one- and two-letter words are not checked). A capitalised one is an unknown *name* only when not sentence-first or after a title; with no entry named and none carried over (`sl.nobody`) the question is refused without a call (`NOT_SAID`), otherwise the model is called, the name is banned and a closing sentence appended. Known gaps: a remembered fact told only with names the reader has met is not caught, and a name-like common word opening a sentence is refused even when innocent. Earlier answers are never replayed, only earlier questions (unknown words blanked; turns noted `unknown name` or `refused: outside knowledge` are dropped by `historyFor` in `ask.js`) and what they were about, checked against the current view. The model is `pick_model(tier)`; a question holds one of 2 slots while it runs (429 `busy`), and `model.timeout` is 120 s where the backend has one (not Claude). Nothing is stored or logged. The Ask tab is hidden only when there is no model (it stays while Ollama is busy); one line names the model answering now, not kept per answer. The thread lives in memory and is cleared with the field (typed, prefilled or restored text) when the position moves back at all, a Finished box is unticked, an earlier book, another order or index is opened, or an edit or merge removes or renames something visible (`revealsLess`: a snapshot of ids, names, profiles, details, ties, events and chapter recaps; not the story recap, which is replaced as the reader goes on). Reading on, into the next book too, keeps it. No spec, schema or protocol change.
8f. **Art sets** (`art.py`, CLI `lorekeeper illustrate`; the store, stage and routes are `web/art.py`, `web/jobs.py`, `web/app.py`): generated pictures, never part of the index document (the schema is closed, nothing in SPEC changes, they stay out of share bundles and registries). An art set is one folder per edition and style behind a `Sink` (`manifest`, `save`, `put`, `read`; `FileSink` is the CLI's folder `art/<textHash>/<style>/`, the web store implements the same four calls): `art.json` (`{"lorekeeperArt": "0.1", textHash, style, world, pictures, appearance, screened, skipped, cost}`, rewritten after every picture) and files `<id>.<ext>` with `p<8 hex>` ids named from the bytes. A picture record has kind `plate|event|portrait|place|thing`, `target` (chapter title, event id or entity id), `from` (the anchor it shows from, compared by ordinal like every `from`), `sources` (the anchors of this book it was written from, always at or before `from`), `references`, `appearance` (entity kinds), the prompt exactly as sent, provider, model, quality, shape, cost, `replaces` (a redraw). The model only proposes: `Illustrator` (the run; `job`, `make_prompt` and `draw` are the pieces the Reader's on-demand drawing calls one at a time, `NotVisible` for a target after the reader's anchor) decides what is drawn, anchors, references, the cap and every drop. **What is drawn:** `main` level is one picture per chapter that has events (its plate: the drawable turning point, else the drawable event whose words the chapter recap shares most, else the recap alone), `all` adds every other drawable moment as an `event` picture, minor events never; *drawable* is one cheap call per chapter (`drawable`: the visible moments, each with a one-sentence frame, cached under `screened` by chapter title, " (2)" for a repeated title); portraits for people and creatures that have a portrait-stage profile or are named by two non-minor events, at the first such profile's anchor, and again (up to `MAX_VERSIONS` per book, `MIN_GAP` blocks apart, the old one kept) when a profile's first sentence gains a look word the last lacked (`LOOK_PROFILE`) or a checked fact or turning point records a wound, death or change of form (`LOOK_STANDING` on top of `portraits.changes_standing`, hedged wording ignored); an entity drawn in an earlier book is not drawn again without such a change, and one whose look the text never shows ("empty" appearance note) is skipped with "skipped: no look described", remembered across resumes. **Prompts:** the writer (the run's cheap text model) sees the passage (the paragraphs the event's `evidence` cites, one either side, at most 600 words, never past the anchor; for a portrait the sampled mention paragraphs), the index content from `gating.view` at the anchor (event and setting, the chapter so far, the chapter's earlier events, the named entities' latest visible profile and facts), the world note and each figure's appearance note, and writes 60 to 120 words of one scene with no names; it also returns `shows`, the figures it draws, and only those keep their note and reference. Checks: `portraits._checked` against the capitalised words of the book up to the anchor (unknown names), hindsight and "now" wording, `ABOUT_THE_TEXT`, a tie word the passage or notes lack, and no person, creature or group name (every token of their names, all books), one rewrite, else the picture is skipped ("dropped: unknown name in prompt", "dropped: name in prompt", "dropped: hindsight wording in prompt"...). Code, not the writer, then appends the notes, the world note, the style sentence (`STYLES`, or the person's own; never an artist's name) and `NO_TEXT`, so notes are verbatim in every prompt. **Consistency:** the *world note* (40 to 80 words, no names, from the first `WORLD_CHAPTERS` = 3 story chapters' recaps, settings and the passages of their first turning points; a later series book inherits the first book's and may append one sentence when its own opening shows a change, then pictures before that sentence's anchor use the older text; `edited: true` is never rewritten); the *appearance note* per person, creature, place and thing (20 to 40 words, role and look only, written once at the first anchor that needs it by a pass that runs before any picture so two pictures never carry two notes, amended with "The same..." on a look change, never rewritten; versioned in `appearance`, a later book reads the earlier manifests); and *references*: the current picture of each entity the scene shows (`latest_picture`, earlier books included), at most 4, most tied in the view first, never anyone else, so two entity ids that are one hidden identity keep two portraits and a scene never borrows the other's face; a look-change portrait carries the previous portrait. **Anchors:** a plate is the chapter's last anchor, an event picture the event's, a portrait, place or thing the latest facet or profile of the entity visible at the position. Because the world note is written from the first three chapters, every picture is held to its anchor (`Illustrator._anchor`, the report's `held`): pictures of those chapters show from the end of chapter 3, never earlier, since a picture may not be written from content after its anchor (a world note with `base` only holds nothing). **Drawing:** `draw` resumes (a record with the same kind, target and anchor is not drawn again), at most `WORKERS` = 3 calls in flight, portraits first (most named first, an entity's versions in order) and then scenes, one quieter rewrite after `ImageRefused` then a recorded skip that is not retried ("refused: ..." with the provider's wording in the report), `ProviderError` retried once, the cost cap (images; stops the run, keeps what was drawn, the last picture's cost standing in when the price is unknown) and `--limit` checked before every call. A series run draws earlier books too (portraits only unless given a level) so that later books inherit their notes and pictures; an earlier book without an EPUB is only read. The text model's cost is reported beside the pictures'. A sample on Dracula with `gemini-nano-banana-2.1` at draft is in `.claude/work/add-art-sets/samples/` (gitignored). **In the web app** the store is `web/art.py` `ArtStore`: `lorekeeper-data/art/<textHash>/<style-slug>/` (the index's `builtFrom` edition, `text_hash(doc)`), a `FileSink` per set (`sink`), one lock per set, `styles` (with `bytes`), `editions`, `find`, `path` (a file is served only when the manifest lists it under its own `<id>.<ext>` name), `remove`, and `take_out` / `put_back` for undo. A set is identified by its slug: `resolve(textHash, style)` gives the slug and the set's stored style text, which every route and the stage hand to `Illustrator`, so "Ink" draws into the "ink" set and an existing manifest is never replaced by an empty one. A pictures run is a `kind: "art"` job on the build queue (`JobManager.submit_art`, `POST /api/library/{key}/art/run` with the art config: style, level `main` or `all`, portraits, quality, provider, model, and a required cap above $0 and at most $500, which the build form fills in as $10; the job's config also names its text `provider` and its `image_provider`, and its JSON carries `index`, the library key). It is refused with 409 while a build writes that index or pictures are being drawn for that edition (`writing` / `drawing`). Its `output` is the index it draws for, which is never written and never deleted with the job, and it neither marks the book as building, nor blocks merges and edits, nor makes Ollama look busy. A build whose config has `art` ends with the same stage after the arcs (`JobManager._art`: phase `art`, events `{"type": "art", done, total, cost}`, `progress.art`, the report under `report["art"]`). The stage is skipped with one log line when there is no image key (taken from `Keys` or the environment, like a text key) or no cloud text model for the prompts. A failure keeps the index and the pictures drawn so far. A stop leaves the build stopped with `progress.resumeFrom: "art"`, and a resume draws the rest without building the index again. Earlier series books are only read, as the CLI's `--prior` does; one whose edition the store rejects is skipped with a log line. Routes:
- `GET /api/library/{key}/art?style=`: the set whole, each picture with its `url`, plus `styles` and `size`. The Reader gates by `from`.
- `GET /api/art/{textHash}/{slug}/{id}`: the file, with the covers' `max-age=86400`.
- `GET /api/art` (every set per book, for Settings) and `DELETE /api/art/{textHash}[?style=]`.
- `GET /api/art/estimate`: pictures, plates, portraits, price and per-chapter drawable counts, with no model call (`Illustrator.counts` when the pipeline has it). An unknown provider or model is 422.
- `POST .../art/prompt`: one text call. It takes `finished`, the reader's finished earlier books; an unfinished earlier book is not read. `p`, an anchor id or the Reader's word fraction gated in finished mode, refuses a target after it with 422 `not-visible`. A missing world note is written first and kept only when the picture is still visible. It answers the price for the chosen provider and quality, `slug` and `inherits`.
- `POST .../art/draw`: draws the person's prompt as given, never softened, with the anchor and references of the pipeline's prompt for the same job, reused from the prompt route for an hour (a locked cache) so there is no second call. A refusal is 422 `refused` with the provider's reason and is not recorded as a skip for later runs.
- `DELETE .../art/{id}`, `POST .../art/{id}/redraw` (`note` put first in the old prompt, the same references, drawn as given; the new record `replaces` the old, which leaves the set) and `PUT .../art/world` (`edited: true`, from the book's first anchor).

Every change to the pictures (a draw, a run's or stage's new pictures, a delete, a redraw, a world note, a set removed) is one journal entry (`Identity.snapshot`, `kind: "art"`, with the empty `keepNames` and `dropNames` the duplicates panel reads, and the removed files copied to `merges/<id>/`). `POST /api/library/{key}/undo/{id}` reverts only the records that entry touched (`art_revert`), so pictures drawn since are never lost. Pictures are not the index, so they and their undo work on community and example indexes too. Every mutating route and undo answer 409 `busy` while pictures are being drawn for that edition.

9. **Validation** (`validate.py`, §6.4): schema check first (later checks assume a valid document), then mechanical rules, then rules that need the book (`check_against_book`) or the series (`check_series`). Passing `prior=None` to `check_index` means the earlier books weren't supplied, so cross-book references become warnings; `[]` means there are no earlier books.
10. **Clients** (`clients/`): programs that consume indexes without any AI. `clients/koreader/lorekeeper.koplugin/` is a thin KOReader plugin (Lua 5.1/LuaJIT): it sends the CREngine XPointer plus the EPUB's `fileHash` to a server's `/v0` routes ("Who is this?" on a selection, "Story so far") and shows only what comes back, without caching any view. Routes live only in `lorekeeper_client.lua`; `lorekeeper_format.lua` is pure Lua. `tests/test_koreader_plugin.py` pins its routes and query parameters to `web/protocol.py`, so change the two together. The JS gating module in `web/static/js/gating.js` (driven by `tests/js/run_conformance.mjs`) is the reference client for local gating. **Rule:** a client that implements a part of the spec (locators, anchor resolution, gating) must pass the conformance suites for that part (`conformance/`) before it counts as supporting it. Clients must never derive positions from percentages or page numbers (SPEC §3.7). A fat client (local gating in Lua) is future work (SPEC §11).

Key format ideas that span several files:
- Every gated item has a `from` anchor; comparisons use the anchor's **ordinal** (position in the `anchors` array), never ids or `seq`.
- `replaces` only points backwards (same book earlier, or an earlier series book), so indexes can be generated forward without editing earlier files. Replaced items become `history`, not deleted.
- Entity ids are series-scoped; each book's index lists only that book's names and facets, and `view()` merges across finished books. `carried` is a denormalized fallback used only when the origin book's index is absent.

## Conventions

- Content rules (SPEC §6) apply when editing example indexes: text-only claims with `evidence`, written as the reader understands things *at* the `from` anchor (no hindsight), at most 8 consecutive words quoted from the book. The validator checks the last rule with `--epub`.
- Example anchors use ids like `ch2.para14` (chapter, paragraph within chapter) with `seq` hints for the Gutenberg edition. Author new anchors by `seq`, then run `fill-anchors`.
- Conformance expected outputs are generated by the reference implementation. When regenerating, review the diff, and keep spoiler properties asserted independently in `tests/test_gating.py`.
- Never restart `lorekeeper web` or kill a generate process while a run is active: check `/api/jobs` and **abort** if anything is running, queued or stopping. CLI and Studio runs share one Ollama.

## Working as lead

In this project Claude Code acts as the lead and delegates feature work to the agents in `.claude/agents/` (spec-keeper, core-engineer, pipeline-engineer, web-engineer, frontend-engineer, client-engineer, docs-writer, and code-reviewer as the gate). The playbook is `.claude/LEAD.md`: scope the feature in `.claude/work/<slug>/brief.md`, give it a worktree and a Herdr space named `lorekeeper: <slug>`, run each worker in a tab named `work: <role>`, have each worker's part reviewed in a pane beside that worker, in its own tab (the `code-reviewer` instructions, run by a Cursor agent on GPT-5.6 Sol so the gate is a different model from the workers), review it once more yourself, then ship. Workers follow `.claude/WORKER.md`.
