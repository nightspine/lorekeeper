Self-hosting

Run the Lorekeeper server on your own machine. It builds indexes for your books, shows them in a Reader, and serves the read-only protocol to your other devices.

Run with Docker

The image bundles the server, the docs and the example library. It runs as an unprivileged user and keeps everything in one volume mounted at /data.

git clone https://github.com/nightspine/lorekeeper.git && cd lorekeeper
docker compose up -d

Then open http://localhost:8765. The compose file pulls the published image ghcr.io/nightspine/lorekeeper for amd64 and arm64. To build from your checkout instead, swap the image line for the commented build: .. To use one command and no compose file:

docker run -d --name lorekeeper -p 8765:8765 -v lorekeeper-data:/data \
  --add-host host.docker.internal:host-gateway \
  -e LOREKEEPER_OLLAMA_URL=http://host.docker.internal:11434 \
  ghcr.io/nightspine/lorekeeper:latest

Add it to an existing compose file

Copy this service into the services: section of your own compose file, and add the volume:

services:
  lorekeeper:
    image: ghcr.io/nightspine/lorekeeper:latest
    ports:
      - "8765:8765"
    volumes:
      - lorekeeper-data:/data
    environment:
      LOREKEEPER_API_TOKEN: ${LOREKEEPER_API_TOKEN:-}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY:-}
      LOREKEEPER_OLLAMA_URL: http://host.docker.internal:11434
    extra_hosts:
      - "host.docker.internal:host-gateway"
    restart: unless-stopped

volumes:
  lorekeeper-data:

Only the port, the volume and the environment matter. LOREKEEPER_API_TOKEN protects the /v0 protocol, a provider key is optional if you build with a cloud model, and LOREKEEPER_OLLAMA_URL points at your Ollama.

Image tags

latest is the newest stable release, 1.2.3 and 1.2 pin a release, and edge is the latest build of the main branch, which may contain unreleased changes. Pin a version for anything you rely on.

Environment variables fill in the defaults of the matching command-line flags, and a flag you pass always wins.

The image's own entrypoint already binds 0.0.0.0:8765 inside the container, so to change the port people use, change only the left side of the port mapping, for example 8080:8765.

Ollama on the host or in compose

The compose file points Lorekeeper at an Ollama running on your machine, through host.docker.internal. On Linux the extra_hosts line in the file makes that name work. On the host, Ollama must accept connections from Docker, so start it with OLLAMA_HOST=0.0.0.0 if the Settings page cannot see it.

To run Ollama in Docker as well, enable the optional service and point Lorekeeper at it:

LOREKEEPER_OLLAMA_URL=http://ollama:11434 docker compose --profile ollama up -d
docker compose exec ollama ollama pull gemma4:12b-it-qat

Models are stored in the ollama-models volume. Inside Docker, Ollama uses the CPU unless you give it a GPU: on Linux with an NVIDIA card and the NVIDIA Container Toolkit, uncomment the deploy block of the ollama service. Docker on macOS cannot pass the GPU through, so a Mac is much faster with Ollama installed on the host, which is why that is the default.

Reverse proxy, token and the Host check

The server checks the Host header against localhost to stop DNS rebinding. When it binds to anything other than a local address, as the container does, that check is switched off, so a proxy can forward books.example.com to it without any extra setting. In exchange, the web app has no login: anyone who can reach the port can build books and change settings. Publish the port only on a trusted network, for example 127.0.0.1:8765:8765, and put a reverse proxy that does its own authentication, a VPN or Tailscale in front of it.

LOREKEEPER_API_TOKEN protects only the /v0 protocol that reader apps use. Set it whenever the server is reachable beyond your own machine, and have the proxy pass Authorization through.

Backups

Everything worth keeping is in the lorekeeper-data volume. Check the Runs page first, then copy it out:

docker run --rm -v lorekeeper_lorekeeper-data:/data -v "$PWD":/backup alpine \
  tar czf /backup/lorekeeper-data.tgz -C /data .

The volume name is prefixed with the compose project name, which is the folder name; docker volume ls shows it. The archive contains secrets.json, so keep it private. To update, run docker compose pull && docker compose up -d, and the volume is kept. If you build from a checkout, run git pull and docker compose up -d --build instead.

Install without Docker

You need Python 3.11 or later and uv.

git clone https://github.com/nightspine/lorekeeper.git && cd lorekeeper
uv sync --extra web --extra claude
uv run --extra web --extra claude lorekeeper web

The server listens on http://127.0.0.1:8765. The claude extra is only needed if you want Claude to build or fact-check indexes. Add --port to change the port and --data to change where it keeps its files.

Library and Book Orbit

The Library lists books, with each book's index versions grouped under it. You can upload EPUBs, or sign in to a Book Orbit server under Settings to browse its books. Only books with an EPUB appear, since comics and PDFs have no text to index, and you choose which Book Orbit libraries to show. A book's EPUB is downloaded the first time you build it.

Series come from Book Orbit, from the EPUB's own metadata, or from you. When you build a book whose earlier series books have no index, the Library warns you, and it can queue a whole series in order so that each book builds on the ones before it. Characters then keep one identity across books.

Models and keys

Building reads a book chapter by chapter, proposes facts for each chunk, checks every claim against the text and writes the index after each chunk.

  • Ollama runs a model on your own machine and sends nothing out. Install it, start it, and pick a model in the build form. A two-chapter run takes tens of minutes on a 16 GB laptop, so start it and come back.
  • Bring your own key. A cloud model is faster and usually better at names and relationships. Claude, OpenAI, Gemini, OpenRouter, Mistral, Groq, xAI and DeepSeek work with your own account, and so does any server that speaks the OpenAI chat API. The book text is sent to the provider you pick, and the build form shows a price estimate before you start (or says the price is unknown for a model it has no price for). After each build a short pass rewrites character descriptions with the cheap model of the provider you built with, about ten cents a novel on the cheapest models, and it is skipped when no key is set.

Where keys come from

Under Settings, each provider has a card with a link to create a key. The key is tested with a free call before it is saved. You can also set it in the environment, which is the easiest way in Docker, and Settings then shows it as coming from the environment, masked. A key saved in Settings wins over the environment.

Keys you enter under Settings are stored in lorekeeper-data/secrets.json, readable only by you, and are shown back masked. They are passed to the model at run time and never written into job records or run logs. The preset model list and prices are a convenience: the model picker also lists the models your key can reach, and you can use any of them.

A server of your own

Choose "Custom server" in Settings and enter its base URL (for example http://localhost:1234/v1 for LM Studio) and the model name it serves. A key is optional. Lorekeeper asks for JSON that matches its schema and falls back to plain JSON mode for servers that do not support schemas. Quality depends on the model: small local models can miss names that a larger model finds. From the command line, use lorekeeper generate --provider custom --base-url URL --model NAME, or --provider openai, gemini and the others with a key in the environment or in a file given to --api-key-file.

Exposing the server

By default the server only answers to localhost. It checks the Host header so that a hostile web page cannot reach it through DNS rebinding, and it requires a custom header on every write so that other sites cannot post to it.

To reach it from a phone or an e-reader, bind to a network address (the Docker image already does):

uv run lorekeeper web --host 0.0.0.0 --api-token-file ~/.lorekeeper-token

With --host set to anything but a local address the Host check is switched off, and anyone who can reach the port can use the whole web app, including building books and changing settings. The bearer token protects only the read-only protocol under /v0, not the web app. Put the server behind a VPN, Tailscale or a reverse proxy that does its own authentication.

For the token, give --api-token (visible in shell history), --api-token-file (first line of the file) or the LOREKEEPER_API_TOKEN environment variable. Clients then send Authorization: Bearer <token>, and discovery stays public so an app can learn that a token is needed. The protocol reference has the details.

Where your data lives

Everything is under lorekeeper-data/ in the directory you started the server from, or under /data in Docker.

PathContents

The exact folder names inside lorekeeper-data/ can change while the project is a draft, so treat the table as a map, not a contract.

Backups

Copy the whole lorekeeper-data/ folder while no run is active. Indexes are plain JSON and can be committed to git. Leave out secrets.json if you share the backup. Commands that rewrite existing indexes, such as profiles and portraits, copy the originals into backups/ first. Check the Runs page before you stop the server, because a build that is killed mid-chunk loses that chunk. A stopped run continues from its last finished chunk with Resume.

Book Orbit reading position

When a book comes from Book Orbit, the Reader asks Book Orbit where you are in it and starts there, with a note saying so. Book Orbit stores the position in whichever dialect the reading app wrote: an EPUB CFI from its web reader and iOS app, a spine file with a percentage from Kobo, a KOReader XPointer, or a whole-book percentage. The server maps the most precise usable one onto the text model with the same locator rules as the protocol, and rounds toward the paragraph before, so it can only under-reveal.

The position acts as a line. Dragging the Reader past it stops at the line, and letting go there asks whether you really have read further. Say yes and the Reader moves on and remembers it, or go back to Book Orbit's position with one click. If Book Orbit cannot be reached, the Reader says so and carries on from where you left it.
