Integrate a reader app

Add a spoiler-safe "who is this?" to your reader. You can gate on the device with the JavaScript client, or ask a server over plain HTTP. Both give the same answer.

Concepts in 200 words

An index is a JSON file for one book. Every fact in it has a from anchor, the paragraph after which the fact may be shown. An anchor is not a page or a percentage. It is a fingerprint: a hash of a paragraph's first twelve words, normalized so that punctuation and letter case do not matter. Your reader holds its own copy of the book, so it computes the same fingerprints and finds each anchor's paragraph in its own edition. That is why one index fits every edition and every font size.

A position is a paragraph, never a screen. Your reader knows where the reader is in its own terms, as a CFI, a word offset or an XPointer, and that is a locator. A locator maps to one paragraph, and that paragraph maps to the last anchor the reader has passed.

Gating is the filter. Given the index and the position, it returns only the items whose anchor the reader has passed, merged across the books of a series the reader has finished. It is a small pure function, so it runs on the device and nothing about the reader's position has to leave it. A server can run the same function if you prefer to keep your app thin.

The next sections show both ways. The specification behind them is section 3 for the text model and section 7 for gating.

The fat client: gate on the device

This path needs the EPUB's XHTML documents and an index. It works offline once the index is cached, and the reading position never leaves the device. The client is one dependency-free ES module, lorekeeper-client.js, plus gating.js next to it. Copy both from src/lorekeeper/web/static/js/. They run in browsers and in Node 22 or later, and any WebView or JavaScript runtime that has DOMParser can use them.

Four calls take you from an EPUB to an answer:

  1. buildEdition(docs) numbers the paragraphs of the spine and fingerprints them (specification 3.1 to 3.3).
  2. new LorekeeperIndex(indexJson, edition) resolves every anchor against that edition once (3.6).
  3. index.view(locator) returns the whole spoiler-safe view at a position (7).
  4. index.lookup(name, locator) answers a tapped name (8.6).

Here is the complete example as a browser module. It reads the EPUB with JSZip, asks the server which index matches the book's text hash, and looks up a name.

app.js

import JSZip from "https://cdn.jsdelivr.net/npm/jszip@3.10.1/+esm";
import { buildEdition, LorekeeperIndex } from "./lorekeeper-client.js";   // copy it and gating.js into your app

const SERVER = "http://localhost:8765";
const xml = (s) => new DOMParser().parseFromString(s, "application/xml");

// 1. Read the EPUB's spine in order. Every itemref counts, linear or not, so the array index is the CFI step.
async function readSpine(file) {
  const zip = await JSZip.loadAsync(file);
  const read = (path) => zip.file(path).async("string");
  const opfPath = xml(await read("META-INF/container.xml")).querySelector("rootfile").getAttribute("full-path");
  const opf = xml(await read(opfPath));
  const manifest = new Map([...opf.querySelectorAll("manifest > item")]
    .map((item) => [item.getAttribute("id"), item.getAttribute("href")]));
  const docs = [];
  for (const ref of opf.querySelectorAll("spine > itemref")) {
    const path = decodeURIComponent(new URL(manifest.get(ref.getAttribute("idref")), "http://x/" + opfPath).pathname.slice(1));
    docs.push({
      spineChild: docs.length,
      linear: ref.getAttribute("linear") !== "no",
      document: new DOMParser().parseFromString(await read(path), "application/xhtml+xml"),
    });
  }
  return docs;
}

export async function open(file) {
  const edition = buildEdition(await readSpine(file));                       // 2. blocks, seq, fingerprints (§3.1 to §3.3)
  const found = await (await fetch(`${SERVER}/v0/lookup?textHash=${edition.textHash}`)).json();
  const indexJson = await (await fetch(SERVER + found.results[0].href)).json();
  return new LorekeeperIndex(indexJson, edition);                            // 3. resolves anchors once (§3.6)
}

// 4. Ask. The locator is whatever your reading system holds.
const index = await open(document.querySelector("input[type=file]").files[0]);
const cfi = "epubcfi(/6/10!/4/2/30/1:0)";
console.log(index.lookup("Holmes", { cfi }));

Two details matter. The array you pass to buildEdition must hold every itemref of the spine, linear or not, so that a CFI step can be turned into an array index. Items marked linear="no" get no blocks but keep their place. And the index is fetched by textHash, so you only ever fetch an index built for your book's text. You can also pass fileHash, isbn or gutenberg to the lookup route.

What comes back

Run against the Gutenberg edition of A Study in Scarlet, the example prints the following. The CFI points into chapter I, paragraph 14, where Stamford first mentions Holmes.

[
  {
    "entity": {
      "id": "holmes", "type": "person", "name": "Sherlock Holmes", "aliases": [],
      "profile": null,
      "facets": [{ "id": "sis.holmes.1", "basis": "stated", "book": "study-in-scarlet",
                   "text": "A man Stamford knows from the hospital's chemical laboratory, who is looking for someone to split the cost of a set of rooms." }],
      "history": []
    },
    "facets": [ ...the same facets array... ],
    "relations": [],
    "events": []
  }
]

The result is an array with one element per matching entity, empty when nothing visible matches. entity is the entity as the view renders it, facets repeats its current facets for convenience, and relations and events list only the visible ones that involve it. Relations appear only when both ends are visible.

Try the same call with the CFI from the locator page, epubcfi(/6/10!/4/2/14/1:12), which sits eight paragraphs earlier. It returns []. Holmes has not been introduced yet, so the lookup finds nothing, and that is the point of the exercise.

For a series, pass the earlier books' indexes and the manifest: new LorekeeperIndex(indexJson, edition, { series, others: [book1Json] }). Options order and finished match the protocol parameters of the same names. index.at(locator) returns just the anchor id.

The thin client: ask the server over HTTP

If your app cannot parse the EPUB, or you want the smallest possible integration, ask a server that holds the book. The server turns the locator into a paragraph and gates for you. The cost is that the reading position is sent to the server, which is fine for a server you run yourself. The server must hold your edition of the book, and tells you with a 409 when it does not. Then fall back to the fat client.

The examples below were run against a local server. Long bodies are trimmed with an ellipsis.

1. Discovery

curl http://localhost:8765/.well-known/lorekeeper

{"lorekeeper":"0.1","name":"Lorekeeper","api":"/v0",
 "capabilities":["lookup","index","series","view","view-cfi","entities"],
 "auth":{"type":"none"}}

Check that view or entities is listed. view-cfi means the server accepts cfi and xpointer locators. If auth.type is bearer, send Authorization: Bearer <token> on every other request.

2. Find the index for your book

curl "http://localhost:8765/v0/lookup?textHash=3ba1a6316fb65ab87f83bbbc65d66b82d0313be6a836e20770dc9571bd8d4ff5"

{"results":[
  {"id":"examples--sherlock-holmes--study-in-scarlet",
   "title":"A Study in Scarlet","match":"text","complete":false,
   "digest":"sha256:1c87e7bcc...fe74a51",
   "href":"/v0/indexes/examples--sherlock-holmes--study-in-scarlet",
   "series":{"id":"sherlock-holmes","book":"study-in-scarlet"},
   "updated":"2026-10-21T00:00:00Z"},
  ...
]}

Results are best first: file (the very same EPUB file), then text (same text), then identifier (probably another edition). Take the first. You do not need the text model for this call: fileHash, the SHA-256 of the EPUB's bytes, is enough if the server holds that exact file, and isbn, gutenberg, openlibrary and wikidata work too.

The textHash is the SHA-256 of every normalized word of every block of the edition, joined by single spaces, in order (specification 3.4). Computing it takes the whole text model, so it suits fat clients. The client module exports textHash and words, and edition.textHash returns it from buildEdition.

3. Fetch the index, with caching

curl -i http://localhost:8765/v0/indexes/examples--sherlock-holmes--study-in-scarlet

HTTP/1.1 200 OK
etag: "sha256:1c87e7bccae416374f7aaf4c50a906ac6b7d299bbf6ff05466add8898fe74a51"
cache-control: private, max-age=0, must-revalidate
content-type: application/json

{"lorekeeper":"0.1","kind":"index","id":"sherlock-holmes.study-in-scarlet", ...}

curl -i -H 'If-None-Match: "sha256:1c87e7bc...fe74a51"' http://localhost:8765/v0/indexes/examples--sherlock-holmes--study-in-scarlet

HTTP/1.1 304 Not Modified

Store the body keyed by the etag and send it back as If-None-Match next time. The ETag equals the digest from lookup, so you can also compare digests without fetching.

4. Ask for a view or a name

Send exactly one position, either an anchor id of the index or one locator form, plus textHash or fileHash to say which edition the locator is about. Here are the same paragraph (chapter I, paragraph 6) as a CFI, an XPointer and a word offset. The server answers each with the same anchor.

# an EPUB CFI
curl -G "http://localhost:8765/v0/indexes/examples--sherlock-holmes--study-in-scarlet/view" \
  --data-urlencode "cfi=epubcfi(/6/10!/4/2/14/1:12)" --data-urlencode "textHash=3ba1a6316fb65ab87f83bbbc65d66b82d0313be6a836e20770dc9571bd8d4ff5"

{"lorekeeper":"0.1","kind":"view",
 "position":{"book":"study-in-scarlet","anchor":"ch1.para05"},
 "coverage":{"complete":false,"through":"ch2.para51","exhausted":false},
 "entities":[{"id":"watson","name":"John H. Watson", ...}, ...],
 "relations":[ ... ], "relationHistory":[], "events":[ ... ],
 "recap":null, "chapters":[],
 "locator":{"position":"ch1.para05","seq":36,"basis":"cfi","exact":true}}

The view is gated in finished mode by default, so the paragraph being read does not count yet. The locator member tells you what the server understood: the anchor, the paragraph number, the form and whether the match was exact.

# a KOReader XPointer, asking who Watson is (inclusive by default for this route)
curl -G "http://localhost:8765/v0/indexes/examples--sherlock-holmes--study-in-scarlet/entities" \
  --data-urlencode "name=Watson" \
  --data-urlencode "xpointer=/body/DocFragment[5]/body/div/p[6]/text().12" \
  --data-urlencode "textHash=3ba1a6316fb65ab87f83bbbc65d66b82d0313be6a836e20770dc9571bd8d4ff5"

{"position":"ch1.para06",
 "entities":[{"id":"watson","type":"person","name":"John H. Watson","aliases":["Watson"],
   "profile":null,"facets":[{"id":"sis.watson.1","basis":"stated","book":"study-in-scarlet","text":"The narrator. Qualified as a doctor ..."}, ...],
   "history":[],"relations":[...],"events":[...]}],
 "locator":{"position":"ch1.para06","seq":36,"basis":"xpointer","exact":true}}

# a spine document and a word offset
curl -G "http://localhost:8765/v0/indexes/examples--sherlock-holmes--study-in-scarlet/view" \
  --data-urlencode "spine=4" --data-urlencode "word=240" --data-urlencode "textHash=3ba1a6316fb65ab87f83bbbc65d66b82d0313be6a836e20770dc9571bd8d4ff5"

{ ... "position":{"book":"study-in-scarlet","anchor":"ch1.para02"}, ...
  "locator":{"position":"ch1.para02","seq":33,"basis":"word","exact":true}}

If the server does not hold your edition, the answer is a problem document and the right response is to fall back to the fat client:

curl "http://localhost:8765/v0/indexes/examples--sherlock-holmes--study-in-scarlet/view?block=3&textHash=0000"

HTTP/1.1 409 Conflict
content-type: application/problem+json

{"type":"https://lorekeeper.dev/problems/edition-not-held","title":"Edition not held","status":409,
 "detail":"This server has no copy of the reader's edition, so it cannot map the locator. ..."}

The complete list of routes, parameters and errors is the protocol reference.

Which mode: finished or inclusive

The same locator gives two different positions, depending on whether the paragraph under the reader counts.

ModeThe paragraph being readUse it forDefault on
finishedDoes not count yet.A view: "what do I know so far", a recap screen, a cast list./view and the client's view()
inclusiveCounts.A name the reader is looking at, such as a tap on the current page./entities and the client's lookup()

The tap-to-lookup case shows why. A reader taps "Holmes" in the paragraph that introduces him. In finished mode the paragraph is not done, so Holmes is not yet known and the lookup comes back empty, which feels broken. In inclusive mode he is visible, with exactly the facts that paragraph supports. The lookup is the one place where the reader is allowed to see what the current paragraph reveals, because they are looking at it. If you cannot tell where the current paragraph ends, use finished. Override the default with inclusive=true|false over HTTP and { inclusive } in the client.

curl -G "http://localhost:8765/v0/indexes/examples--sherlock-holmes--study-in-scarlet/entities" --data-urlencode "name=Holmes" \
  --data-urlencode "cfi=epubcfi(/6/10!/4/2/30/1:0)" --data-urlencode "textHash=3ba1a6316fb65ab87f83bbbc65d66b82d0313be6a836e20770dc9571bd8d4ff5"
-> position "ch1.para14", one entity: Sherlock Holmes with one facet

curl -G "http://localhost:8765/v0/indexes/examples--sherlock-holmes--study-in-scarlet/entities" --data-urlencode "name=Holmes" \
  --data-urlencode "cfi=epubcfi(/6/10!/4/2/30/1:0)" --data-urlencode "textHash=3ba1a6316fb65ab87f83bbbc65d66b82d0313be6a836e20770dc9571bd8d4ff5" \
  --data-urlencode "inclusive=false"
-> position "ch1.para12", "entities": []

Spoiler safety checklist

Section 7.4 of the specification lists what a client must not do. In practice:

  • Never display, prefetch into the interface, or search over an item the gating step did not return. That includes full-text search over an index you hold: search the view, not the file.
  • Do not reveal an item because an anchor failed to match. Follow the resolution rule: an unresolved anchor takes the location of the next resolved one, so a missing paragraph can only make the app reveal later.
  • Show no counts, placeholders or orderings that disclose hidden items. "3 more facts about this character" is a spoiler. So is a sorted list whose gaps reveal what is missing.
  • Do not derive a position from a percentage of the whole book or from a page number. Use a locator. The only fraction allowed is progress inside one document, and it is approximate.
  • When a locator cannot be mapped, fail. Do not guess. When two guesses are possible, pick the earlier paragraph.
  • Let the reader override which books they have finished only as an explicit choice, never as a default.
  • Treat index text as untrusted. Show it as text, never as markup.

Testing your port

The conformance/ folder is the contract. It holds fourteen gating cases and twenty-two locator cases, as plain JSON, and any language can read them. The conformance page has their exact shapes.

  • Gating cases (conformance/*.json) give index files, an optional series, and a position. They assert the whole view. Compare it with JSON equality, array order significant. Cases cover a position before the first anchor, facets replaced by later facts, a series whose earlier book is finished or not, and carried entities.
  • Locator cases (conformance/locators/*.json) give an EPUB, an index and a locator, and assert the block number, whether it is exact, and the anchor in each mode. They need the Project Gutenberg EPUB, which the README shows how to download.
  • Fingerprints are covered by the locator cases too: if your fingerprints differ from the reference, anchors will not resolve and every case fails at the first step.
uv run lorekeeper conformance            # run the Python reference against every case
uv run lorekeeper conformance --update   # regenerate expected output after an intended change
node tests/js/run_conformance.mjs        # the JavaScript client against the gating cases

You pass a locator form's cases if you support that form. A server that accepts a form must pass them as well.

Porting notes

  • Fingerprint parity is everything. A word list is built by applying Unicode NFKC, then full case folding, deleting the joiners (hyphen, apostrophes, soft hyphen and a few invisible characters), then taking every maximal run of letters, marks and numbers. The fingerprint is the SHA-256 of the first twelve words joined by a space, as UTF-8, written as the first sixteen lowercase hex characters. A tiny difference changes every anchor.
  • Full case folding is not lowercasing. German sharp s becomes "ss", and the Greek final sigma folds to an ordinary sigma. The JavaScript client carries a small table of the differences from toLowerCase, generated from Python. In Swift, use the Foundation or ICU folding that implements full case folding, and in Kotlin or Java use ICU4J. Do not use a locale-sensitive lowercase.
  • The Unicode version caveat. Case folding, normalization and the letter, mark and number categories all depend on the Unicode version of your platform. Text with characters added after your version can fingerprint differently from the reference. The result is an unresolved anchor, which can only reveal later, never earlier. Section 3.2 and open question 1 of the specification discuss it. The conformance cases pin the behaviour for the characters they use.
  • SHA-256 is the only hash. The JavaScript client ships a small synchronous implementation so it needs no platform crypto. Use your platform's own.
  • The text model is the contract, not the HTML. Paragraph-level blocks are defined by section 3.1: the listed elements, nested blocks excluded, empty ones dropped, and a fallback for books that set every paragraph in a div. Reuse the client's parser as a reference when your DOM differs.
  • Lua. Whether KOReader's Lua runtime can do Unicode categories and SHA-256 cheaply is open question 1 in the specification. The KOReader plugin avoids the question by being a thin client.

Example thin client: the KOReader plugin

The repository ships a KOReader plugin in clients/koreader/lorekeeper.koplugin/, inside the repository you cloned. It is a good reference for a thin client, because KOReader already holds a CREngine XPointer for the reader's position and the EPUB's file hash. It sends those to the server and shows the answer.

  1. Copy the lorekeeper.koplugin folder into KOReader's plugins/ directory on your device.
  2. Restart KOReader.
  3. Open the plugin's menu and set the server address, for example http://192.168.1.20:8765. If the server has a token, enter that too.

The server must hold the same EPUB file you read, which is the case when you built the index from it, and must be reachable from the device. See exposing the server.
