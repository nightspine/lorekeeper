Share an index

An index is one JSON file, so sharing it needs no server. Three commands turn it into a bundle, file it in a registry and publish static lookup files that any reader app can query with one GET.

This page is the tooling side of section 8.7 of the specification. Nothing in the index changes for sharing: a shared index is a plain index document.

The web app does the same from a book's page, and also finds and adds indexes others shared: see Community indexes.

Make a bundle

uv run lorekeeper share examples/dracula/dracula.json -o dracula.share.json
uv run lorekeeper share INDEX --epub book.epub -o bundle.json
uv run lorekeeper share book2.json --series series.json --derived-from sha256:... -o bundle2.json

share copies the index and removes label and fileHash from every edition. A label is often a local file name, and a file hash describes one person's copy. builtFrom stays, because it says which edition the anchors were written for.

It refuses an index that fails the schema or the validator, and one whose licence is not CC0-1.0 or CC-BY-4.0. A book in a series needs --series with the manifest.

With --epub it also runs the checks that need the book, and records them as attestations marked by: "builder":

AttestationWhat it says
book-checksHow many anchors the index has, how many resolve in your EPUB, and how many errors the validator found. The bundle is not written if there are errors.
spoiler-gateFor each name, the first paragraph where the book uses it. early counts names the index would show before the book does.

The EPUB's text hash must be one of the index's editions. The report lists up to five early names so you can look at them. They are not stored in the bundle. An early above 0 does not stop you from sharing; it is recorded.

What is in a bundle

{ "lorekeeper": "0.1", "kind": "share",
  "index": { ... },
  "series": { ... },
  "derivedFrom": "sha256:...",
  "attestations": [ { "kind": "book-checks", "by": "builder", ... } ] }

series is required when the index belongs to a series. derivedFrom is the digest of a shared index this one improves. The schema is schema/share.schema.json.

Check and add

uv run lorekeeper registry check bundle.json --publisher mina-m --source registry/
uv run lorekeeper registry add   bundle.json --publisher mina-m --source registry/

check writes nothing. add runs the same checks, then files the bundle. A registry treats a bundle as input from a stranger, so the checks are strict. They refuse a bundle when:

  • the file is over 5 MB (checked before it is parsed), or it fails share.schema.json;
  • the index fails the schema or the validator;
  • the licence is not CC0-1.0 or CC-BY-4.0;
  • an edition still has a label or fileHash;
  • an attestation is not by builder;
  • the same bytes are already a version of that listing;
  • the listing was removed;
  • the publisher name is not valid;
  • a book in a series needs an earlier book the publisher has not shared. Share the books in publication order.

Paths are built only from the validated publisher and the slug, which is the index id lowercased with every character outside a-z0-9- turned into -. Sharing the same book again adds a version. Old versions never change.

add writes this tree in the registry source folder:

indexes/mina-m/dracula/listing.json
indexes/mina-m/dracula/v1.lore.json
indexes/mina-m/dracula/series.json      (books in a series)
removed.json

The listing records the digest, the versions, the licence, whether people edited the index, and the attestations of the latest version. The registry adds its own validates attestation. To take a listing down:

uv run lorekeeper registry remove mina-m/dracula --source registry/ --reason "Requested by the rights holder"

That deletes the listing and appends it to removed.json. The same id cannot be added again.

A listing that later books of the series require is not removed unless you pass --with-dependents, which removes those books too. add likewise refuses a new version of an earlier book that would break the later ones the publisher has already shared.

Build the static site

uv run lorekeeper registry build registry/ -o build/registry/ \
  --base-path /lorekeeper-registry --name "Lorekeeper community registry"

This writes a folder for any static host. The build is deterministic and clears v0 first. It checks every listing against its schema and every index against its digest, and fails if one does not match.

.well-known/lorekeeper
v0/lookup/text/{textHash}.json
v0/lookup/gutenberg/{id}.json   (also isbn, openlibrary, wikidata)
v0/listings/{publisher}/{slug}.json
v0/indexes/{publisher}/{slug}/v{N}.lore.json
v0/series/{publisher}/{slug}.json
v0/removed.json

Every href carries the base path. Look a book up with one request:

curl https://nightspine.github.io/lorekeeper-registry/v0/lookup/text/6211b79150ee12207b34736872d807d9074170062dbc03fee71075ef8a38f00d.json

A static host cannot send the digest as an ETag. A client must hash the index bytes it fetched and compare them with the digest in the result before using them. A mismatch is a failed fetch. The protocol reference has the details.

Who vouches

A registry that cannot hold a book cannot check it. So book-checks and spoiler-gate are the publisher's word, and only validates is the registry's. Nothing verifies the builder's numbers. A client shows who vouches for each one and does not blend them into a single score. Signatures are not part of this yet.
